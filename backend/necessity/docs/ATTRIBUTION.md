# Failure Attribution —— 失败根因归因

> 设计文档 v1
> 目标：把「任务失败了」变成「**因为什么失败、下一步该改哪里**」

---

## 0. 一页摘要

**问题**：现有评测工具只输出 pass / fail 率。**没有告诉你为什么失败。** 于是「90 次失败」只是一句废话——不知道是哪一环坏了，也不知道该优化什么。

**方案**：建立失败分类体系，从 Agent 轨迹中提取确定性信号，规则优先 + LLM 补充，输出「分类 + 证据」。

**三个产出**：
1. **失败构成** —— 哪类失败最多
2. **改进优先级** —— 先修哪个（按占比排）
3. **归因准确率** —— 归因本身也要被验证（元评测）

**差异化**：现有评测停在 pass/fail 率。**没有人系统地做失败归因。**

---

## 1. 问题定义

### 1.1 现状的不足

| 现有输出 | 能回答 | 不能回答 |
|---|---|---|
| pass/fail 率 | 做得怎么样 | 为什么没做到 |
| 轮次 / token | 成本 | 钱花在哪了 |
| 工具调用次数 | 做了多少动作 | 哪个动作是错的 |
| 最终 diff | 改了什么 | 哪一处导致失败 |

### 1.2 目标

对每次失败的尝试 `attempt`，输出：

```
category      ∈ 失败分类体系
confidence    ∈ [0,1]
evidence      = 支撑该结论的具体轨迹片段
improvement   = 对应的改进方向
```

### 1.3 核心指标

| 指标 | 定义 |
|---|---|
| **归因准确率** ⭐ | 与人工标注一致的比例 |
| **每类 P / R** | 分类别统计 |
| **混淆矩阵** | 哪些类容易混（用于修正分类体系） |
| **失败构成分布** | 各类占比（指导改进优先级） |

## 2. 失败分类体系（设计核心）

### 2.1 设计原则

1. **MECE** —— 互斥且尽可能完备
2. **可操作** —— 每一类对应一个明确的改进方向（**这是分类存在的意义**）
3. **可扩展** —— 首版 9 类，允许后续细分

### 2.2 首版分类

| # | 分类 | 含义 | **对应改进方向** |
|---|---|---|---|
| 1 | `planning` | 任务分解错、顺序错、方向偏 | 改规划提示词 / 加 plan 校验 |
| 2 | `context_missing` | 关键信息没进上下文（没读 / 被压缩掉） | 改检索 / **Context Paging** |
| 3 | `context_stale` | 用了过期信息做决策 | 加失效校验 |
| 4 | `tool_use` | 选错工具 / 参数错 / 未处理工具失败 | 改工具描述与签名 |
| 5 | `edit_error` | 编辑本身写错（语法、逻辑、改错位置） | 加强编辑前检查 |
| 6 | `constraint_drift` | 越界改动 | **Constraint Guard** |
| 7 | `thrashing` | 反复改-回滚，不收敛 | **Diff Reducer 定位** |
| 8 | `environment` | 依赖缺失 / 网络 / 权限 / flaky 测试 | **修环境（非 Agent 问题）** |
| 9 | `capability` | 模型推理或知识不足 | 换模型 / 拆小任务 |
| 10 | `task_issue` | 任务本身不可完成 / 需求矛盾 | **改任务定义（非 Agent 问题）** |

### 2.3 关键区分：谁的锅

**8、10 两类不是 Agent 的问题。** 归因出这两类，说明该修的是环境或任务定义。

> **做出这个区分是本设计的重要价值** —— 否则会把「环境缺依赖」误判成「Agent 能力不足」，然后去换模型，白费功夫。

### 2.4 多因失败

一个失败常常有多重原因。设计为：

```
primary        = 主导原因（用于统计）
contributing[] = 次要原因列表（用于完整报告）
```

**统计时只用 primary**，避免重复计数。

## 3. 归因方法

### 3.1 三层架构

```
Layer 1  确定性信号（规则）     覆盖明确案例（预期 60~70%）
   ↓ 未命中
Layer 2  LLM 辅助判定           处理需要语义理解的案例
   ↓
Layer 3  人工抽样验证           算准确率，修正体系
```

### 3.2 为什么规则优先

| 用纯 LLM | 用规则优先 |
|---|---|
| 不可复现 | ✅ 可复现 |
| 慢、贵 | ✅ 快、免费 |
| 无法解释 | ✅ 信号即证据 |
| 可能被轨迹里的文本误导 | ✅ 只看客观信号 |

**但纯规则不够** —— 有些原因需要语义理解（例如「这个改动与任务目标无关」）。所以规则打底，LLM 补漏。

### 3.3 关键要求：归因必须携带证据

```json
{
  "attempt_id": "task_012#3",
  "primary": "context_missing",
  "contributing": ["thrashing"],
  "confidence": 0.82,
  "method": "rule",
  "evidence": [
    {"turn": 3, "signal": "never_read",
     "detail": "未读过 src/parser/tokenizer.py"},
    {"turn": 12, "signal": "modified_unread",
     "detail": "第 12 轮修改了该文件"},
    {"turn": 8, "signal": "compaction",
     "detail": "发生上下文压缩，丢失第 2~6 轮工具结果"}
  ],
  "improvement": "启用 Context Paging，避免压缩后丢失已读内容"
}
```

> **没有证据的归因等于猜。** 面试官问「你怎么知道是这个原因」，证据就是答案。

## 4. 信号提取（Layer 1）

### 4.1 前置依赖

**需要 Agent 输出结构化轨迹。** 最低要求：

| 事件 | 必要字段 |
|---|---|
| `turn_start` | turn 序号 |
| `llm_response` | 思考文本、工具调用意图 |
| `tool_call` | 工具名、参数 |
| `tool_result` | 成功/失败、错误类型、输出摘要 |
| `file_read` | 路径、行范围、内容 hash |
| `file_write` | 路径、改动行数 |
| `compaction` | 触发时的 token 数、丢失的消息范围 |
| `edit_revert` | 哪一处被回滚 |
| `test_run` | 测试集、结果 |

> **Aurora 已有 `sse_events.py`（62 个事件常量）**，可作为轨迹来源；不足的部分补充埋点。

### 4.2 确定性信号表

| 信号 | 提取方式 | 指向分类 | 置信度 |
|---|---|---|---|
| **环境类异常** | 异常栈含 `ImportError` / 连接超时 / 权限拒绝 | `environment` | 高 |
| **测试 flaky** | 同配置多次运行结果不一致 | `environment` | 高 |
| **约束违反** | 读 Guard 的违反日志 | `constraint_drift` | 高 |
| **工具参数错误** | 工具返回 `invalid-arguments` 类错误 | `tool_use` | 高 |
| **工具未处理失败** | 工具返回失败后，Agent 未做任何补救 | `tool_use` | 中 |
| **改了没读过的文件** | 有 `file_write` 但无对应 `file_read` | `context_missing` | 中高 |
| **压缩后重读同一文件** | `compaction` 后出现已读文件的 `file_read` | `context_missing` | 高 |
| **反复改同一处** | 同一位置 `file_write` + `edit_revert` ≥ 3 次 | `thrashing` | 高 |
| **轮次耗尽无进展** | 达最大轮次且最终测试仍 fail，且 diff 无净变化 | `thrashing` / `capability` | 中 |
| **上下文接近上限** | 多轮 token 接近阈值 | `context_missing` | 中 |
| **任务定义矛盾** | 人工预标注（任务集元数据） | `task_issue` | 高 |
| **测试本身不可能通过** | 基线 `T(∅) = fail` | `task_issue` | 高 |

### 4.3 信号优先级

多个信号命中时，按优先级决定 `primary`：

```
environment / task_issue        ← 最高（非 Agent 问题，先排除）
    ↓
constraint_drift                ← Guard 的客观日志
    ↓
thrashing
    ↓
tool_use
    ↓
context_missing / context_stale
    ↓
planning / edit_error / capability   ← 依赖 Layer 2 补齐
```

**理由：先排除「不是 Agent 的锅」，再归因到 Agent。**

## 5. LLM 辅助判定（Layer 2）

### 5.1 触发条件

Layer 1 无高置信信号命中时触发。

### 5.2 输入设计

**不投喂完整轨迹**（太长且噪声大），而是投喂**结构化摘要**：

```
任务：<task.md 内容>
结果：fail
轮次：18 / 上限 20

轨迹摘要：
  turn 1-3   读取 src/parser/{parser,tokenizer}.py
  turn 4     修改 parser.py 的 parse()
  turn 5     测试失败（3 个用例）
  turn 6-9   反复修改 parse() 与 tokenizer.py
  turn 10    回滚到 turn 4 状态
  turn 11-18 再次尝试，测试仍失败

最终 diff：parser.py +42/-8，tokenizer.py +15/-2
失败测试：test_parse_async, test_tokenizer_stream
```

### 5.3 输出约束

**强制要求输出证据引用**：

```
{
  "primary": "planning",
  "confidence": 0.7,
  "evidence": [
    "turn 6-9 在 parse() 与 tokenizer.py 之间反复横跳，说明未先确认改动边界",
    "turn 10 整体回滚，说明前序改动方向有误而非细节问题"
  ]
}
```

**若无法给出具体证据 → 必须输出 `unknown`**，而不是硬猜一个分类。

> `unknown` 是合法输出。**强行分类会污染统计。**

## 6. 归因本身的验证（元评测）

> **这一节是本设计区别于「随便做个分类器」的地方。**

### 6.1 为什么必须验证

归因可能不准。**如果不报告准确率，整个失败构成分布就不可信**，基于它的改进决策也会错。

### 6.2 验证方法

1. **人工标注**：随机抽 50 个失败案例，人工判定 primary 分类
2. **计算**：
   - 整体准确率
   - 每类 Precision / Recall
   - 混淆矩阵
3. **报告**：
   - 准确率（含置信区间）
   - **最容易混的两类** → 说明分类体系需要调整
   - 规则层 vs LLM 层各自的准确率（看 LLM 层是否真的有用）

### 6.3 分类体系迭代

若某两类混淆率 > 30%，说明边界不清，应：

- 要么合并
- 要么拆分并给出更明确的判定规则

**分类体系是迭代出来的，不是一次设计出来的。**

## 7. 数据模型

```sql
-- 尝试记录
CREATE TABLE task_attempt (
  attempt_id   TEXT PRIMARY KEY,
  task_id      TEXT NOT NULL,
  config       TEXT NOT NULL,     -- 模型 / 配置 / 对照组
  result       TEXT NOT NULL,     -- pass | fail
  turns        INTEGER,
  tokens       INTEGER,
  duration_sec REAL,
  diff_stats   TEXT               -- {files, hunks, added, removed}
);

-- 归因结果
CREATE TABLE failure_attribution (
  attempt_id   TEXT PRIMARY KEY REFERENCES task_attempt,
  primary_cat  TEXT NOT NULL,
  contributing TEXT,              -- JSON 数组
  confidence   REAL NOT NULL,
  method       TEXT NOT NULL,     -- rule | llm | human
  evidence     TEXT NOT NULL,     -- JSON 数组
  improvement  TEXT,
  attributed_at REAL
);

-- 人工标注（ground truth）
CREATE TABLE human_label (
  attempt_id   TEXT PRIMARY KEY,
  primary_cat  TEXT NOT NULL,
  labeler      TEXT,
  note         TEXT
);

-- 轨迹事件（若 Agent 已有 trace 存储，可复用）
CREATE TABLE agent_event (
  attempt_id  TEXT NOT NULL,
  turn        INTEGER,
  event_type  TEXT NOT NULL,
  payload     TEXT,
  ts          REAL
);
```

## 8. 边界情况与失败模式

| # | 情况 | 处理 |
|---|---|---|
| 1 | 无轨迹（Agent 不支持 trace） | 该尝试标记 `unattributable`，不计入统计 |
| 2 | 轨迹不完整（缺关键事件） | 降级为 LLM 层；报告中标注置信度低 |
| 3 | 多因且都显著 | 输出 `primary` + `contributing`，统计只用 primary |
| 4 | Layer 1 和 Layer 2 结论冲突 | 以 Layer 1 为准（客观信号优先），记录冲突供分析 |
| 5 | 任务本身不可完成 | 任务集元数据预标注，最高优先级，不参与 Agent 能力统计 |
| 6 | 基线测试就是挂的 | 标记 `task_issue`，从实验集剔除 |
| 7 | 人工标注者之间不一致 | 双人标注 + 计算一致性（Kappa），低于阈值则修订标注规范 |
| 8 | 归因结果用于改进后仍无提升 | 说明归因错误或改进方向错，回到 §6 复核 |

## 9. 实验设计

### 9.1 假设

- **H1**：失败可以稳定归因（准确率显著高于随机）
- **H2**：加上确定性信号后，归因准确率高于纯 LLM
- **H3**：失败分布能指导改进（按占比排序改进，效果优于随意改进）

### 9.2 任务与数据

- 任务集：25~30 个任务
- 每任务多配置跑（不同模型 / 有无护栏），**主动制造失败样本**
- 目标：收集 ≥ 120 个失败尝试
- 人工标注其中的 50 个作为验证集

**注意：需要主动制造失败。** 若都用最强模型，失败样本会很少，统计不显著。

### 9.3 对照

| 组 | 归因方法 |
|---|---|
| **A** | 纯 LLM（把轨迹丢给模型让它分类） |
| **B** | 纯规则（只用 §4.2 信号表） |
| **C** | **规则 + LLM 补充（本设计）** |

### 9.4 指标

| 指标 | 期望 |
|---|---|
| **归因准确率** ⭐ | C > B > A |
| 每类 P / R | 报告全部 |
| 混淆矩阵 | 找出边界不清的类对 |
| `unknown` 占比 | 越低越好，但**不允许为降低它而强行分类** |
| 失败构成分布 | 描述性统计 |

### 9.5 成功 / 失败判据

**成功**：准确率显著高于随机基线（9 类随机 ≈ 11%），且 C 优于 A

**失败**：
- 准确率接近随机 → 分类体系或信号表有问题
- `unknown` 占比 > 40% → 信号覆盖不足
- LLM 层准确率低于规则层 → 说明 LLM 层在帮倒忙，应移除

## 10. 风险与回退

| 风险 | 严重度 | 缓解 |
|---|---|---|
| 归因不准，误导优化方向 | 🔴 高 | §6 元评测；报告准确率；低置信度标 `unknown` |
| 轨迹缺失/不完整 | 🟠 中 | 补齐埋点；不完整的标 `unattributable` |
| 分类体系边界不清 | 🟠 中 | 用混淆矩阵迭代修正 |
| LLM 层不可复现 | 🟠 中 | 固定温度 0；结论必须带证据；与规则冲突时以规则为准 |
| 失败样本太少不显著 | 🟡 低 | 主动用弱模型/严格配置制造失败样本 |

**回退路径**：归因是**离线分析**，不干预 Agent 运行。即使完全不准，也只是分析结论不可用，不影响系统。

## 11. 实施计划

| 阶段 | 时间 | 交付 | 验收 |
|---|---|---|---|
| **P0** | 1 天 | 分类体系定稿 + 数据表 | 9 类定义清晰 |
| **P1** | 2 天 | 轨迹事件采集（复用/补齐埋点） | 能录出完整轨迹 |
| **P2** | 2 天 | 确定性信号提取（§4.2） | 规则命中率可测 |
| **P3** | 1 天 | 规则层分类器 | 出第一版归因 |
| **P4** | 2 天 | LLM 辅助层 + 证据约束 | 兜底可用 |
| **P5** | 2 天 | 人工标注 50 例 + 算准确率 | **拿到准确率** |
| **P6** | 1 天 | 混淆矩阵 + 分类体系迭代 | 修正边界 |

**总计约 1.5 周。**

**若只有 1 周**：P0 + P1 + P2 + P3 + P5（不做 LLM 层）。仍能报告「纯规则归因准确率 X%」——这已经是有价值的结论。

## 12. 面试要点

**Q1：这和普通日志分析有什么区别？**
→ 日志是原始记录；归因是**带分类体系和证据的结论**。关键区别在于：① 分类对应明确的改进方向；② 每个结论附带可核验的轨迹证据。

**Q2：为什么不用 LLM 直接分类？**
→ 可以，但不能只用它。LLM 不可复现、无法解释、可能被轨迹文本误导。**确定性信号优先，LLM 只补规则覆盖不到的。**

**Q3：怎么保证归因是对的？**
→ **归因本身要被验证**。人工标注 50 例做 ground truth，算准确率和混淆矩阵。**不报告准确率的归因等于猜。**

**Q4：如果两类总是混淆怎么办？**
→ 说明边界不清，用混淆矩阵驱动分类体系迭代——要么合并，要么拆分并给出更明确的判定规则。**分类体系是迭代出来的。**

**Q5：失败样本太少怎么办？**
→ 主动制造。用弱模型、严格配置、缩短轮次上限跑同一批任务，让失败变成可控变量。

**Q6：这个能力最大的价值？**
→ 三层：① 把「90 次失败」从废话变成可分析数据；② 指导改进优先级（哪类最多先修哪个）；③ 它能**横向对比不同模型/配置的失败构成**——这是别人给不出的。

**Q7：为什么先排除 environment 和 task_issue？**
→ 因为这两类**不是 Agent 的锅**。不先排除，就会把「环境缺依赖」误判成「模型能力不足」，然后去换模型，白费功夫。

## 附：术语表

| 术语 | 含义 |
|---|---|
| **归因** | 判定失败的根因类别 |
| **primary / contributing** | 主因 / 次因 |
| **元评测** | 对归因本身的准确率评测 |
| **混淆矩阵** | 分类错误的分布，用于修正分类体系 |
| **unattributable** | 因轨迹缺失而无法归因 |
| **unknown** | 有轨迹但无法给出有证据的归因（合法输出） |
