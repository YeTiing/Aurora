# Context Paging —— 符号级文件上下文分页

> **所属**：Necessity 系统的 `backend/necessity/context/` 模块（**能力 1**）
> **入口**：`SYSTEM.md` ｜ **集成**：`INTEGRATION.md` ｜ **评测**：`EVAL.md` ｜ **基础设施**：`INDEX.md`
>
> 设计文档 v1
> 目标：解决「上下文压缩导致 Agent 失忆 → 重复读同一文件」的结构性问题

---

## 0. 一页摘要

**问题**：Agent 读过的文件内容存在对话历史里，压缩时被摘要替代；Agent 失忆后重读，上下文又满，再压缩——形成负反馈循环。

**方案**：把文件内容从对话历史搬到**对话外的状态表**，对话里只保留**符号级索引**；需要细节时按符号精确取，而不是整文件重读。

**核心不是省 token，是让长任务不因压缩而失忆。** 省 token 是副产品。

**先行者与差异**：MemGPT / Letta 做过对话历史的分页记忆。本设计的三点不同：
1. 分页对象是**代码文件**，不是对话历史
2. 寻址粒度是**符号**，不是页/块
3. 符号索引复用 **LSP `documentSymbol`**，不自己切块

---

## 1. 问题定义

### 1.1 可度量的现象

在一次会话中，令：

- `R(f)` = 文件 `f` 被 `read_file` 完整读取的次数
- `R_waste(f)` = 其中「状态表已有最新内容且可用」的读取次数

**待优化量**：`Σ R_waste(f) / Σ R(f)`

### 1.2 实测证据（Aurora 代码位置）

| 位置 | 代码 | 后果 |
|---|---|---|
| `backend/context/context_manager.py` | 阈值 `0.85` 触发压缩，LLM 生成 handoff 摘要，`keep_recent=4` | 旧消息中的文件内容被摘要替代 |
| `backend/agent/graph.py:305` | `for h in history[-8:]` | 仅最近 8 条保留原始内容 |
| `backend/tools/file_rw.py` | 无任何读缓存（仅 `MAX_READ_SIZE` / `SKIP_DIRS`） | 每次读都真实访问磁盘 |
| `backend/tools/file_rw.py:164` | 返回 `stat.st_mtime` 但未持久化 | 元数据算了就丢 |

### 1.3 因果链

```
读文件 → 内容作为 tool result 进入对话历史
   ↓
上下文达阈值（85%）
   ↓
压缩：旧消息 → LLM 摘要
   ↓
文件内容丢失，仅剩「读过 f」这一事实
   ↓
Agent 判定信息不足 → 重读
   ↓
上下文再次达阈值 → 再压缩
```

**这是一个结构性循环**：只要「用压缩控制上下文」这一策略不变，该循环必然存在。

## 2. 根因分析

### 2.1 四个独立成因

| # | 成因 | 性质 | 本设计是否解决 |
|---|---|---|---|
| 1 | 压缩吞掉工具返回 | 存储位置错误 | ✅ 核心解决 |
| 2 | 文件内容无独立存储 | 缺少持久层 | ✅ 核心解决 |
| 3 | 编辑后行号漂移，需重读定位 | 寻址方式脆弱 | ⚠️ 部分（改为符号寻址） |
| 4 | 模型保守倾向「不确定就重读」；子 Agent 不共享上下文 | 行为/架构 | ⚠️ 部分（提示词 + 跨 Agent 共享） |

### 2.2 关键区分：这不是「记忆」问题

| | 记忆系统 | 本问题 |
|---|---|---|
| 时间尺度 | 跨会话、跨天 | **单次会话内** |
| 代表方案 | ContextDB / MemFlow / Memex | —— |
| 解决的问题 | 「记住用户偏好 / 上次的方案」 | 「**本次会话内不要重复读**」 |

**结论**：本设计属于**上下文生命周期管理**，不属于长期记忆系统。二者正交，不应混用同一套机制。

### 2.3 合法重读 vs 浪费重读

**必须先划清边界，否则优化会破坏正确性。**

| 合法重读 ✅ | 浪费重读 ❌ |
|---|---|
| 编辑后验证改动是否落地 | 压缩后遗忘 |
| 文件被外部工具修改（git checkout / formatter） | 同一轮内重复读 |
| 内容过期（Agent 记忆中的内容与磁盘不一致） | 多个子 Agent 各读一遍 |
| 状态表首次遇到该文件 | 读一个片段却拉了整个文件 |

**本设计只消除右列。**

## 3. 相关方案与不足

| 方案 | 做法 | 不足 |
|---|---|---|
| MemGPT / Letta | 对话历史分页到外部存储 | 对象是对话历史，不是代码；无符号寻址 |
| 常规 context offloading | 大工具结果外置，对话留指针 | **只有一个指针不够**——Agent 不知道文件里有什么，仍会整读 |
| 单纯提高压缩阈值 | 少压缩 | 治标；上下文仍会满 |
| 单纯加大窗口 | 减少压缩次数 | 成本线性上升，且仍会满 |
| 提示词叮嘱「不要重复读」 | prompt 约定 | **用会被压缩的东西解决被压缩的问题**，逻辑上不成立 |

**共同缺口**：没有人在**符号粒度**上做代码上下文的分页与寻址。

## 4. 设计目标与非目标

### 4.1 目标

| # | 目标 | 度量 |
|---|---|---|
| G1 | 降低重复读取率 | `Σ R_waste / Σ R` 下降 ≥ 50% |
| G2 | 降低 token 消耗 | 同一任务集总 token 下降 ≥ 20% |
| G3 | **不降低任务完成率** | 完成率下降 ≤ 2%（硬约束） |
| G4 | 减少压缩触发次数 | 压缩次数下降（因上下文占用下降） |
| G5 | 可降级 | 状态表不可用时，行为退化为现状，**不报错** |

### 4.2 非目标

- ❌ 不做跨会话长期记忆（那是另一个问题）
- ❌ 不做语义检索 / 向量召回
- ❌ 不做多语言（先只支持 Python）
- ❌ 不修改 Agent 的主循环结构
- ❌ 不做自动代码理解 / 摘要生成（L2 摘要可选，非首版）

## 5. 总体架构

```
                       ┌─────────────────────────────┐
   读取请求 ──────────→ │  read_file 工具（改造）      │
                       └──────────┬──────────────────┘
                                  │
                    ┌─────────────┴──────────────┐
                    ▼                            ▼
          ┌──────────────────┐        ┌────────────────────┐
          │ 文件状态表        │        │ 对话上下文          │
          │ （对话外，持久）  │        │ （受影响，会压缩）  │
          │                  │        │                    │
          │ content          │        │ 仅 symbol index    │
          │ content_hash     │        │ + hash + 行数      │
          │ symbols_json     │        │                    │
          │ token_count      │        │                    │
          └────────┬─────────┘        └────────────────────┘
                   │
                   ▼
          ┌──────────────────┐
          │ recall 工具      │ ← Agent 按符号精确取回
          │ （新增）          │
          └──────────────────┘

          ┌──────────────────┐
          │ 符号索引          │ ← LSP documentSymbol
          │ （可独立实现）    │
          └──────────────────┘
```

**支点：状态表在对话之外，压缩器碰不到它。**

## 6. 详细设计

### 6.1 数据模型

拆成两张表：**内容按工作区共享，读取记录按会话隔离。**

```sql
-- 表 1：文件内容（工作区级，多会话共享）
CREATE TABLE file_content (
  workspace     TEXT NOT NULL,     -- 工作区绝对路径
  path          TEXT NOT NULL,     -- 相对路径
  content       TEXT NOT NULL,     -- 全文（对话外）
  content_hash  TEXT NOT NULL,     -- sha256 前 16 位
  size          INTEGER NOT NULL,
  mtime         REAL NOT NULL,
  symbols_json  TEXT,              -- ⚠️ 已移除，见下方说明
  token_count   INTEGER,           -- 全文 token 数（预算用）
  indexed_at    REAL,
  PRIMARY KEY (workspace, path)
);
-- ⚠️ 修正：此表【不存符号索引】。L1 符号索引查基础设施的 symbols 表：
--     SELECT id, name, kind, start_line FROM symbols
--     WHERE workspace = ? AND file = ? AND content_hash = ?
-- 详见 INTEGRATION.md §6（唯一真源原则）

-- 表 2：会话读取记录（会话级）
CREATE TABLE file_read_log (
  session_id  TEXT NOT NULL,
  workspace   TEXT NOT NULL,
  path        TEXT NOT NULL,
  read_count  INTEGER DEFAULT 0,   -- 本会话读了几次
  validity    TEXT NOT NULL,       -- fresh | stale | unknown
  last_read_at REAL,
  PRIMARY KEY (session_id, workspace, path)
);
```

**为什么拆两张：** 文件内容是客观事实，与是谁在读无关；「我读过什么、内容还新不新」是会话状态。混在一起会导致多会话互相污染。

### 6.2 分层表示

**关键约束：对话里只放一个裸指针是不够的。** Agent 不知道文件里有什么，仍然会整读。必须有索引层。

| 层 | 内容 | 典型 token | 暴露时机 |
|---|---|---|---|
| **L0** 文件清单 | `src/parser.py` | ~5/文件 | 始终 |
| **L1** 符号索引 | `parse:12, Tokenizer:45` | ~8/符号 | 默认 |
| **L2** 符号摘要 | 每个符号一句话 | ~30/符号 | 可选，按需 |
| **L3** 全文 / 片段 | 实际代码 | ~2000/文件 | `recall` 拉取 |

**对话中的实际呈现：**

```
<file_state>
src/parser.py   @a3f2c1  120L  [parse:12, Tokenizer:45, Token.err:60]
src/utils.py    @7b2e09   80L  [load:5, dump:30]
</file_state>
```

约 40 token，替代原先的 ~2000 token，**压缩比 ≈ 98%**。

`@a3f2c1` 为内容哈希前缀，Agent 用它判断内容是否变化。

### 6.3 工具接口

#### `read_file`（改造后）

保持原签名，行为改变：

| 参数 | 行为 |
|---|---|
| 默认 | 若状态表命中且 `fresh` → 返回 L1 索引；否则真读并建条目 |
| `force=True` | 强制真读，刷新状态表 |
| `mode="full"` | 真读并返回全文（等价现状） |

> **兼容性要求**：现有调用不带新参数时，必须仍然可用。默认行为改变是本设计的一部分，但要有 `force` / `mode="full"` 逃生口。

#### `recall`（新增）

```
recall(path, mode="symbols")               → L1 符号索引
recall(path, symbol="parse")               → 该符号的完整实现
recall(path, lines=[12, 45])               → 行范围
recall(path, grep="tokenize")              → 文件内搜索，返回匹配行 + 上下文
```

**为什么按符号寻址是关键：**
Agent 的意图单位是符号（「我要看 parse 函数」），不是行号。按行寻址会迫使 Agent 先知道行号，从而退化回整读。

**预算控制**：`recall` 结果超过 `recall_token_budget`（默认 1500）时：
1. 先返回签名 + 前 N 行
2. 附注 `[... 还有 M 行，用 lines=[x,y] 取]`

**不允许静默截断** —— 静默截断会让 Agent 以为看全了。

### 6.4 失效与一致性

#### 状态机

```
unknown ──真读成功──→ fresh
   ▲                    │
   │                    │ 文件 hash 变化 / patch 后
   │                    ▼
   └────删除/读失败──  stale
```

| 状态 | 含义 | Agent 侧动作 |
|---|---|---|
| `fresh` | 状态表内容与磁盘一致 | 可用索引，recall 直接来自状态表 |
| `stale` | 怀疑不一致 | 必须 `recall`（recall 内部先真读校验） |
| `unknown` | 无记录 | 必须真读 |

#### 快速检测与权威判定

```
读请求
  ↓
比 (size, mtime)  ── 相同 ──→ 视为 fresh（快速路径，不读磁盘）
  ↓ 不同
计算 content_hash ── 相同 ──→ 刷新 mtime，仍为 fresh
  ↓ 不同
标记 stale → 真读 → 更新 → fresh
```

**注意 mtime 精度**：部分文件系统 mtime 精度为 1 秒，快速连续修改可能 mtime 相同。因此 `(size, mtime)` 只作快速排除，**权威判定必须是 content_hash**。

#### Agent 自身改动后的处理

Agent 通过 `apply_patch` 修改文件时，**不立即信任 patch 结果**：

1. patch 应用后，标记该文件为 `dirty`
2. 下次访问时先校验 `content_hash`（一次文件读取）
3. 校验通过 → 用 patch 后的内容更新状态表 → `fresh`
4. 校验失败 → 退化为真读

**为什么不做「直接用 patch 更新内容」**：patch 的上下文行匹配可能偏离预期，累积误差会导致状态表与磁盘长期不一致，而这是**静默**的——最危险的一类 bug。

> 若后续实测发现校验开销可接受，可升级为「patch 后异步校验」。

### 6.5 与压缩器的契约

**这是本设计能否成立的关键接口。**

定义两条不变量：

> **不变量 1**：压缩过程**不得**读写 `file_content` 表。
> **不变量 2**：每次压缩完成后，必须向摘要注入当前会话的 file_state 索引。

注入格式（由 `compaction_hook(session_id) -> str` 生成）：

```
## 已读文件（内容在外部状态表，可用 recall 按符号取回）
src/parser.py  @a3f2c1  120L  [parse:12, Tokenizer:45, Token.err:60]
src/utils.py   @7b2e09   80L  [load:5, dump:30]
```

**效果**：Agent 压缩后仍知道
1. 读过哪些文件
2. 每个文件里有哪些符号
3. 内容版本（hash）

从而**不必重读**即可继续工作。

**边界**：若某会话读取文件超过 `max_index_entries`（默认 50），注入时按 `last_read_at` 倒序截断，并注明 `[还有 N 个文件未列出]`。

### 6.6 提示词契约

**机制必须被 Agent 理解才能生效。** 这段话是设计的一部分，不是可选项：

```
关于文件读取：
- 你看到的是【符号索引】，不是文件内容。
- 修改任何符号之前，必须先 recall 该符号的完整实现，不要凭索引猜测。
- 索引中的 @hash 是内容版本。若某文件你记得读过，但 hash 变了，说明它已被修改，必须重新 recall。
- 需要通读全文时才用 read_file(mode="full")；不要为了「确认一下」而整读。
```

**没有这段约定，Agent 会：**
- 看到索引觉得信息不足 → 仍然整读
- 或更糟：**以为索引就是全部，直接改代码**

## 7. 边界情况与失败模式

| # | 情况 | 处理 | 降级后行为 |
|---|---|---|---|
| 1 | 状态表不可用 / 损坏 | 捕获异常，全部走真读 | 等价现状，功能丢失但不报错 |
| 2 | LSP 不可用 | 无符号索引 → 只存 L0 + 全文 | 仍省「重复读」，但无符号寻址 |
| 3 | 文件被删除 | 标记 `stale` + 记录不存在 | 真读返回错误（与现状一致） |
| 4 | 文件过大（> `MAX_READ_SIZE`） | 不建条目 | 现状行为 |
| 5 | 二进制文件 | 不建条目 | 现状行为 |
| 6 | 同一文件并发读 | 状态表加锁 / 幂等 upsert | —— |
| 7 | 压缩注入超长 | 按 `last_read_at` 截断 + 注明 | —— |
| 8 | patch 后 hash 校验失败 | 退化为真读 | 现状行为 |
| 9 | 会话结束 | `file_read_log` 可清理；`file_content` 保留 | —— |
| 10 | 工作区路径变更 | 按 `workspace` 隔离，互不影响 | —— |

**总原则：任何异常路径都必须能降级回真读。** 优化不能以「读不到文件」为代价。

## 8. 实验设计

### 8.1 假设

- **H1**：完整方案相比现状，token 消耗显著下降
- **H2**：完整方案相比「只有指针无分层」，token 消耗进一步下降
- **H3**：完成率不下降

### 8.2 对照组

| 组 | 配置 | 用途 |
|---|---|---|
| **A** | 现状（文件内容进对话） | 基线 |
| **B** | 状态表 + 裸指针（**无符号索引**） | 验证「分层」是否必要 |
| **C** | 完整方案（状态表 + 符号索引 + recall） | 实验组 |

**B 组是这套实验的关键**：它隔离出「分层/符号寻址」单独的贡献。若 C 不比 B 好，说明真正的价值只来自「外置」而非「符号寻址」，**结论要相应改写**。

### 8.3 任务集要求

**必须能触发多次压缩**，否则测不出差异。

- 任务类型：跨多文件的重构 / 特性开发
- 每个任务预期：修改 ≥5 个文件、≥15 轮交互
- 规模：15~20 个任务
- 同一任务，A/B/C 三组各跑一次，**同一模型、同一温度、同一初始快照**

### 8.4 指标

| 指标 | 定义 | 期望 |
|---|---|---|
| **总 token 消耗** | 单任务累计 | C < B < A |
| **read_file 调用次数** | 计数 | C < A |
| **重复读取率** | `R_waste / R` | C 显著低于 A |
| **压缩触发次数** | 计数 | C < A |
| **任务完成率** ⭐ | 验收测试 pass 率 | **C ≈ A（下降 ≤2%）** |
| **recall 调用次数** | 计数 | 观察用（若接近 0 说明 Agent 没在用它） |

### 8.5 成功 / 失败判据

**成功**：`token 下降 ≥ 20%` **且** `完成率下降 ≤ 2%`

**失败**（任一条成立即判定优化失败）：
- 完成率下降 > 5%
- recall 调用次数接近 0（说明机制没被用起来）
- token 反而上升（说明索引开销超过了收益）

> **必须有「实验可能失败」的预期。** 上下文信息减少有可能让 Agent 判断变差，导致完成率下降。**如实记录，不要为了好看调参。**

## 9. 风险与回退

| 风险 | 严重度 | 缓解 |
|---|---|---|
| Agent 不理解机制，仍整读 | 🔴 高 | 提示词契约（§6.6）；若无效，改在工具返回值里主动提示 |
| Agent 以为索引是全文，直接改代码 | 🔴 高 | 索引里显式标注 `[仅索引，未加载内容]` |
| 完成率下降 | 🟠 中 | §8.5 判据；降到 A 组配置 |
| 状态表与磁盘不一致（静默） | 🟠 中 | hash 权威校验；不用 patch 直接更新 |
| 索引开销 > 收益 | 🟡 低 | 小文件（< 50 行）不退化为索引，直接给全文 |
| LSP 索引延迟 | 🟡 低 | didChange 后等诊断；拿不到索引则降级为 L0 |

**回退路径**：本设计是**可开关的**。`context_paging.enabled = false` 时行为完全等于现状，无需回滚代码。

## 10. 实施计划

| 阶段 | 时间 | 交付 | 验收 |
|---|---|---|---|
| **P0** | 1 天 | 埋点：统计现状的 `R`、`R_waste`、压缩次数、token | 拿到基线数字 |
| **P1** | 2~3 天 | `file_content` 表 + 读写封装 + 失效判定 | 单测覆盖状态机 |
| **P2** | 2 天 | 符号索引接入（LSP `documentSymbol`） | 给定文件能产出 L1 |
| **P3** | 2 天 | `recall` 工具 + `read_file` 改造 | 工具可用，带逃生口 |
| **P4** | 1 天 | 压缩契约（`compaction_hook`）+ 提示词 | 压缩后索引正确注入 |
| **P5** | 2~3 天 | 实验：A/B/C 三组跑任务集 | **拿到数字** |

**总计约 2 周。**

**若只有 1 周**：P0 + P1 + P3（不做符号索引，只做状态表 + 全文外置），验证「外置」单独的收益。产出弱一些但仍有数字。

## 11. 面试要点

**Q1：这算记忆系统吗？**
→ 不是。记忆是跨会话的长期存储；这是**单次会话内的上下文生命周期管理**。两者正交。

**Q2：为什么不能用一个提示词解决？**
→ 问题由压缩器造成，而提示词本身也会被压缩。**用会被压缩的东西解决被压缩的问题，逻辑上不成立。**

**Q3：为什么不直接把上下文窗口调大？**
→ 成本线性上升，且仍会满。本质是「信息该存在哪里」的问题，不是「窗口多大」的问题。

**Q4：为什么按符号寻址，而不是按行？**
→ Agent 的意图单位是符号。按行寻址会迫使它先知道行号，从而退化回整读。

**Q5：怎么保证 Agent 不会因为信息变少而犯错？**
→ 两条：① 索引里显式标注「仅索引，未加载内容」；② 提示词要求修改前必须 recall。另外实验里把「完成率不下降」设为硬约束。

**Q6：和 MemGPT 的区别？**
→ MemGPT 分页的是对话历史。这里分页的是**代码文件**，寻址粒度是**符号**，索引来自 **LSP**。

**Q7：这个优化最可能怎么失败？**
→ 两种：① Agent 不理解机制，索引白建；② 信息减少导致完成率下降。所以实验设计里 B 组（无符号索引）和「完成率硬约束」是必须的。
