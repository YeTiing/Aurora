# Minimal Diff Reducer —— Agent 改动的必要性最小化与致败定位

> **所属**：Necessity 系统的 `backend/necessity/reduce/` 模块（**能力 3**）
> **入口**：`SYSTEM.md` ｜ **集成**：`INTEGRATION.md` ｜ **评测**：`EVAL.md` ｜ **基础设施**：`INDEX.md`
>
> 设计文档 v1
> 目标：把 Agent 生成的 diff **自动缩减到最小必要子集**，并定位「是哪一块改坏了」

---

## 0. 一页摘要

**问题**：Agent 改完代码后，diff 里混着**必要改动**和**多余改动**。没人知道哪些是必要的，只能人工 review；测试挂了也不知道是哪一块导致的。

**方案**：用 **Delta Debugging**（逐块回退 + 测试判定）自动求出 diff 的最小必要子集，同时定位致败改动。

**三个产出**：
1. **最小 diff** —— 只留必要的，review 负担下降
2. **冗余清单** —— 列出多余改动及其证明（「删掉它测试仍通过」）
3. **致败定位** —— 测试挂了，直接指出是哪一块

**附带价值**：它产出一个可量化的指标 —— 「Agent 的改动中，多余部分占多少」。
（注：该方向已有研究，见 §1.3；本设计的差异在判定更严格 + 工程更可行。）

**与 Context Paging / Constraint Guard 的关系**：
- Constraint Guard 是**事前**预防越界
- Minimal Diff Reducer 是**事后**清理越界
- 两者互补，不是替代

## 1. 问题定义

### 1.1 形式化

设一次 Agent 任务生成了改动集合 `D = {d₁, d₂, ..., dₙ}`（`dᵢ` 为一块改动）。

定义测试函数：

```
T(S) ∈ {pass, fail, error}    // 对改动子集 S ⊆ D 应用后运行测试的结果
```

基线：`T(∅)` = 不做任何改动时的测试结果。

### 1.2 两个不同的问题

| 目标 | 前提 | 求什么 | 用途 |
|---|---|---|---|
| **必要性最小化** | `T(D) = pass` | 最小 `D' ⊆ D` 使 `T(D') = pass` | 找出**冗余**改动 |
| **致败定位** | `T(D) = fail` 且 `T(∅) = pass` | 最小 `D'' ⊆ D` 使 `T(D'') = fail` | 找出**致败**改动 |

**注意两者方向相反**：一个是找「最小通过集」，一个是找「最小失败集」。

### 1.3 相关研究（诚实修正）

> ⚠️ **早期版本在这里写了「为什么现在没人做」——这是错的。**
> 经过检索，**过编辑 / 冗余改动确实已有研究**。下面如实列出。

| 已有工作 | 做什么 | 与本设计的关系 |
|---|---|---|
| [**TRIM**: Reducing AI-Generated Code Slop via Agent Trajectory Minimization](https://huggingface.co/papers/2607.18161) | 通过**轨迹最小化**减少 AI 生成的"代码垃圾" | 最接近的工作 |
| [nreHieW/over-editing](https://github.com/nreHieW/over-editing) | 度量 Agent 的过编辑行为 | 度量的定义不同 |
| [over-edit-measure](https://skillsmp.com/es/creators/daedalus/skills/skills-over-edit-measure) | 度量过编辑的 Agent Skill | 启发式度量 |
| [To Add Is Machine, To Delete Is Human](https://www.semanticscholar.org/reader/665fb6f77d5fdb61dee1aed555af8ecb4ce2d6ae) | 度量 LLM 编辑中的**删除回避**倾向 | 互补视角 |
| [A Catalogue of Evaluation Metrics for LLM-Based Multi-Agent Frameworks](https://dl.acm.org/doi/10.1145/3786167.3788430) | 提出 12 个新的评测维度 | 说明该方向已受关注 |

### 1.4 那么本设计的差异化在哪（收窄后的说法）

**不能说"没人做过"，只能说以下几点不同：**

| 维度 | 已有工作 | 本设计 |
|---|---|---|
| **冗余的判定依据** | 多为**启发式度量**（行数、编辑次数、LLM 判断） | **可证明的定义**：用测试做 oracle，「删掉它测试仍通过」才算冗余 |
| **最小化的对象** | TRIM 最小化**轨迹**（Agent 的动作序列） | 最小化**最终 diff**，且分两个方向（必要性 / 致败定位） |
| **工程可行性** | 未强调大仓库场景 | 用代码结构图做**一致性组** + 影响面**选测试**，把单次判定从 30 秒压到 2 秒 |
| **与前置/后置能力的闭环** | 单独工具 | 与 Constraint Guard（事前）+ Context Paging（事中）+ Attribution（归因）组成闭环 |

**诚实结论**：**这是个已被关注的领域，本设计是「更严格的判定 + 更可行的工程实现」，不是首创。**

> 面试时**不要**说"这个指标没人测过"。正确的说法是：
> "过编辑已经被研究（比如 TRIM），但它们多用启发式度量。我用测试做 oracle 给出**可证明的**冗余定义，并且用代码结构图解决了大仓库上跑不动的问题。"

### 1.5 旧做法的缺陷（仍然成立）

| 现有做法 | 缺陷 |
|---|---|
| 人工 review 整个 diff | 成本高；无法区分必要与冗余 |
| 看 diff 行数 | 行数多 ≠ 有冗余（合法重构可能很大） |
| lint / 静态检查 | 只能发现语法/风格问题，判断不了「这块改动对目标有没有用」 |
| Agent 自我说明 | Agent 会声称所有改动都必要（不可信） |
| 测试 pass/fail | 只给结论，不告诉你哪一块在起作用 |

**表内旧做法的共同缺口**：**没有用「测试作为 oracle」来判定单块改动的必要性。**

> 但注意 §1.3 的修正 —— TRIM 等工作已经在做类似的事，**本设计的差异化是「判定更严格 + 工程更可行」，不是「第一个做」**。

## 2. 理论基础

### 2.1 Delta Debugging

源自 Andreas Zeller 的 delta debugging（`ddmin` 算法），原本用于**自动缩小导致程序失败的输入**。

**核心思想**：把输入切成 `n` 份，逐份删除，若删除后失败现象仍存在，说明这一份无关，永久移除；否则二分加密，继续尝试。

**迁移到本问题**：

| 原算法 | 本设计 |
|---|---|
| 输入 = 导致 crash 的数据 | 输入 = Agent 生成的 diff |
| 判定 = 程序是否 crash | 判定 = 测试是否通过 |
| 输出 = 最小致错输入 | 输出 = 最小必要改动集 / 最小致败集 |

### 2.2 复杂度

经典 `ddmin` 最坏情况 `O(n²)` 次判定，典型情况接近 `O(n log n)`。

**这里必须优化**，因为每次判定要跑一次测试：

- `n = 20` 块改动 → 最坏约 400 次测试运行
- 若单次测试 30 秒 → 3.3 小时，**不可接受**

优化手段见 §6.3 与 §7。

## 3. 关键设计问题：粒度与一致性组

> **这是本设计最容易做错的地方，单独成章。**

### 3.1 朴素做法为什么错

若按 **hunk 级别**独立回退，会遇到**耦合改动**：

```
hunk 1: 修改 def parse(text, strict=False)      ← 改了签名
hunk 2: 调用点 parse(t) → parse(t, strict=True) ← 跟着改
```

**单独回退 hunk 1（签名改回去）**：
- 调用点仍传 `strict=True` → **类型检查/运行时报错**
- 测试必然失败
- 算法判定「hunk 1 是必要的」→ **误判**

**实际上 hunk 1 和 hunk 2 是一个原子单元，必须同进同退。**

### 3.2 一致性组（Coherence Group）

**定义**：一组改动 `G ⊆ D`，满足「整体应用时项目处于可编译/可解析状态，缺少任何一个成员则不可编译」。

#### ⚠️ 早期版本的算法错误（已修正）

早期写成「对**每对**组做可编译性检查，反复直到无合并」：

```
for each pair (Gi, Gj):          ← O(n²)
    if not compilable(revert(Gi ∪ Gj)): merge(Gi, Gj)
重复直到无合并
```

**这是错的**，两个原因：

1. **复杂度不可接受**：`n=60` hunks → 约 1800 次检查；且类型检查是**秒级**，不是毫秒级 → 约 30 分钟
2. **与本节声称的「廉价剪枝」自相矛盾**：真正毫秒级的是语法解析，**类型检查是秒级的**

#### 正确做法：先做廉价传播，再对结果做一次检查

```
阶段 1  符号归属      每个 hunk → 它触及的符号（按行范围匹配 documentSymbol）
                     成本：毫秒级，无需编译
        ↓
阶段 2  调用边传播    若 hunk A 改了符号 S，且 hunk B 触及 S 的调用方
                     → A、B 并入同组
                     成本：调用图查询，毫秒级（有缓存）
        ↓
阶段 3  导入边传播    若 hunk A 改了模块 M 的导出，且 hunk B 改了 M 的导入方
                     → 并入同组
                     成本：import 表查询，毫秒级
        ↓
阶段 4  分组校验      对【每个组】做一次增量类型检查（每组 1 次，不是两两）
                     失败 → 该组并入最小依赖集后重试（最多 2 轮）
                     成本：秒级 × 组数
```

**复杂度**：`O(n)` 图查询 + `O(m)` 次类型检查（`m` = 组数，通常 `m ≪ n`）。

**关键洞见：阶段 1 单独不够。**

```
hunk 1 改 def parse(...)          → 触及符号 parse
hunk 2 改调用点 caller 内部        → 触及符号 caller
```

**两者触及的是不同符号**，单纯按符号聚类合并不了它们。**必须靠阶段 2 的调用边传播** —— 查出 `caller` 调用了 `parse`，才能把它们并成一组。

#### 成本分级（诚实版）

| 检查 | 实际成本 | 用在哪 |
|---|---|---|
| 语法解析（tree-sitter） | **毫秒级** | 阶段 1 前的快速排除 |
| 符号范围匹配 | **毫秒级** | 阶段 1 |
| 调用图 / import 表查询 | **毫秒级**（有缓存） | 阶段 2、3 |
| **类型检查（pyright）** | **秒级** | 仅阶段 4，每组一次 |

**设计原则：把秒级的检查压到最少次数。** 这正是「先传播后校验」的意义。

### 3.3 降级路径

若缺少调用图（基础设施未就绪）：

| 降级级别 | 做法 | 代价 |
|---|---|---|
| **L1（有调用图）** | 完整四阶段 | 无 |
| **L2（无调用图）** | 阶段 1 + **文件级保守合并**（同文件所有 hunk 归一组） | 组偏大 → 最小化结果偏粗，但**不会误判** |
| **L3（无符号解析）** | 所有 hunk 归为**一个大组** | 退化为「全有或全无」，无最小化能力 |

**宁可组偏大（结果保守），也不要组偏小（导致误判）。** 因为误判会给出错误结论，而保守只是精度差。

## 4. 总体架构

```
Agent 完成任务，产出 diff D
        ↓
┌──────────────────────────────────────┐
│ 1. 切分：D → {d₁...dₙ}                │
│ 2. 聚类：构造一致性组 {G₁...Gₘ}        │  ← 可编译性剪枝
└──────────────┬───────────────────────┘
               ▼
       ┌───────────────┐
       │ 判定 T(D)      │
       └───┬───────┬───┘
      pass │       │ fail
           ▼       ▼
   ┌──────────┐  ┌──────────┐
   │必要性最小化│  │ 致败定位  │
   │ 求最小通过集│  │ 求最小失败集│
   └─────┬────┘  └────┬─────┘
         ▼            ▼
   最小 diff     致败块 + 最小反例
   + 冗余清单
         ↓
   报告 + 可选自动回退
```

**测试执行子系统**（性能关键路径）：

```
候选子集 → 干净快照（worktree）→ 应用改动 → 静态检查 → 选择测试 → 运行 → 记录
                                                  ↑
                                    用影响面分析决定跑哪些测试（见 §7.1）
```

## 5. 详细设计

### 5.1 改动切分

从统一 diff 格式切出改动块。建议粒度：

| 粒度 | 单位 | 适用 |
|---|---|---|
| **hunk** | diff 的 `@@` 块 | **默认** |
| 符号 | hunk 内的符号边界 | 可选，更细 |
| 行 | 单行 | 仅当 hunk 很大时 |

**hunk 过大时**（如一个 hunk 有 50 行）应向下切分到符号级，否则最小化结果太粗。

### 5.2 一致性组构造

> 完整论证见 §3.2。**不要用两两枚举**（那是 `O(n²)` 次秒级类型检查）。

```
输入：hunks = [h1, ..., hn]，以及基础设施（符号表 / 调用图 / import 表）
输出：groups = [G1, ..., Gm]

阶段 1  符号归属
    for h in hunks:  touched[h] = symbols_in_range(h.line_range)
    groups = 按 touched 交集做并查集合并          # 毫秒级

阶段 2  调用边传播
    for h in hunks:
        for s in touched[h]:
            for caller in callgraph.callers_of(s):
                for h2 in hunks:
                    if caller in touched[h2]: union(h, h2)   # 毫秒级（有索引）

阶段 3  导入边传播
    for h in hunks:
        for m in modules_exported_by(h):
            for h2 in hunks:
                if m in modules_imported_by(h2): union(h, h2)

阶段 4  分组校验
    for g in groups:
        if not compilable(revert(g)):
            g = g ∪ minimal_dependencies(g)      # 最多重试 2 轮
```

**复杂度**：`O(n)` 图查询 + `O(m)` 次类型检查（`m` = 组数）。

**注意阶段 2 的必要性**：改签名（符号 `parse`）与改调用点（符号 `caller`）触及**不同符号**，阶段 1 合并不了，必须靠调用边传播。

**降级**（无调用图时）：退化为**文件级保守合并**（同文件 hunk 归一组）。组偏大只会让结果变粗，**不会导致误判**。

### 5.3 搜索算法

**必要性最小化**（目标：最小通过集）

```python
def minimize_necessary(groups, D, test):
    """求最小 G ⊆ groups 使 T(G) == pass"""
    current = groups
    n = 2
    while len(current) >= 2:
        subsets = split(current, n)
        reduced = False
        for s in subsets:
            if test(s) == PASS:
                current = s
                n = max(n - 1, 2)
                reduced = True
                break
        if not reduced:
            if n >= len(current):
                break
            n = min(n * 2, len(current))
    return current
```

**致败定位**（目标：最小失败集）

同一算法，判定条件改为 `test(s) == FAIL`。

**剪枝与加速**：
1. **结果缓存**：同一子集不重复测试（用子集的哈希做键）
2. **单调性假设 + 校验**：假设「改动越少越可能 pass」，据此优先试小集合。**但必须校验**——改动间可能有反直觉的交互（加一块改动反而让另一个测试通过）
3. **并行**：不同子集在独立 worktree 里并行跑
4. **预算上限**：超过 `max_test_runs`（默认 200）时提前终止，返回当前最优解并标注「未收敛」

### 5.4 测试执行环境

**副作用隔离**（必须）：

| 方案 | 优点 | 缺点 |
|---|---|---|
| `git worktree` | 轻量、隔离干净、快 | 需要 git 仓库 |
| 复制目录 | 无 git 依赖 | 慢、占空间 |
| `git stash` 原地切换 | 最快 | 不安全，会污染工作区 |

**建议**：`git worktree`；非 git 仓库降级为复制目录。

**每次测试的流程**：
```
1. 创建/复用干净快照
2. 应用候选改动子集
3. 静态检查（不过 → 直接判 ERROR，不跑测试）
4. 选择要跑的测试（见 §7.1）
5. 运行 → 记录 {subset_hash, result, duration}
6. 清理
```

### 5.5 输出格式

```json
{
  "task_id": "...",
  "original_diff": {"files": 5, "hunks": 18, "lines_added": 120, "lines_removed": 30},
  "baseline_test": "pass",
  "final_test": "pass",

  "necessary": {
    "hunks": ["h1","h2","h5","h7","h11"],
    "lines_added": 42, "lines_removed": 8
  },
  "redundant": [
    {"hunks": ["h3"], "reason": "移除后测试仍通过",
     "location": "src/utils.py:45-60", "lines": 16},
    {"hunks": ["h9","h10"], "reason": "移除后测试仍通过",
     "location": "src/parser.py:120-133", "lines": 14}
  ],

  "metrics": {
    "redundancy_ratio": 0.65,          // 冗余行 / 总改动行
    "test_runs": 47,
    "converged": true,
    "duration_sec": 812
  }
}
```

**对失败场景**，输出改为 `culprit` 字段，指出最小致败集合。

## 6. 工程约束（决定可行性）

> 这一章决定方案能不能落地，比算法本身更重要。

### 6.1 测试速度是硬约束

若单次测试 30 秒、搜索需要 50 次判定 → 25 分钟。**这在交互式场景不可接受。**

**解法：用影响面分析缩小测试范围**

不是每次都跑全量测试，而是：

```
候选改动子集 S
   ↓
用调用图/影响面分析，找出 S 触及的符号
   ↓
反向查「哪些测试覆盖了这些符号」
   ↓
只跑这些测试
```

**这把单次测试从「全量 30 秒」降到「子集 2 秒」，是方案可行的前提。**

> 注：这一步依赖代码结构图（Context Paging / CodeGraph 的调用图能力）。**没有它，本方案的工程成本会高一到两个数量级。**

**降级方案**（无影响面分析时）：按文件路径匹配测试文件（`src/parser.py` → `tests/test_parser.py`）。

### 6.2 非确定性测试（flaky）

**flaky 测试会彻底破坏判定可靠性**：同一子集两次跑出不同结果 → 最小化结果随机。

**处理策略**：
1. **预筛**：正式最小化前，对基线跑 3 次；结果不一致的测试标记为 flaky，**从判定集合中排除**
2. **重试**：单次失败时重跑 2 次；仍失败才判定 FAIL
3. **记录**：报告中注明「排除了 N 个 flaky 测试」

### 6.3 预算控制

搜索必须有硬上限，否则可能跑几小时：

| 预算项 | 默认值 | 超限行为 |
|---|---|---|
| `max_test_runs` | 200 | 终止，返回当前最优 + `converged: false` |
| `max_wall_time` | 15 分钟 | 同上 |
| `max_hunk_count` | 60 | 超过则先做文件级粗最小化 |

### 6.4 与 Agent 循环的集成点

**三种集成方式，成本递增**：

| 方式 | 说明 | 侵入性 |
|---|---|---|
| **离线工具** | 把 diff 和仓库路径喂给 CLI，输出报告 | 无 |
| **任务结束钩子** | Agent 标记任务完成后自动触发 | 低 |
| **编辑后即时** | 每次 apply_patch 后增量更新一致性组 | 高 |

**建议首版做「离线工具」**——零侵入，可独立验证，也最容易跑出实验数字。

## 7. 边界情况与失败模式

| # | 情况 | 处理 |
|---|---|---|
| 1 | 非 git 仓库 | 降级为目录复制 |
| 2 | 测试本身依赖外部服务/网络 | 该类任务不纳入实验集 |
| 3 | 全部改动都必要（无冗余） | 正常输出，`redundancy_ratio = 0` |
| 4 | 全部改动都冗余（删完测试还过） | 输出警告：**Agent 的改动对目标无贡献** |
| 5 | `T(∅) = fail`（改动前测试就是挂的） | 无法判定，直接报错退出 |
| 6 | 改动间存在反直觉交互 | 单调性假设失效 → 算法仍能收敛，但可能非全局最优，报告中标注 |
| 7 | 单个 hunk 内部不可分割 | 保持 hunk 整体，粒度退化 |
| 8 | 测试超时 | 记为 `error`，保守视为「不可移除」 |
| 9 | 磁盘/时间预算耗尽 | 返回当前最优 + 未收敛标记 |
| 10 | Agent 改动包含新文件 | 新文件整体视为一个一致性组 |

**总原则：宁可返回「未收敛的最优解」，也不要返回错误结论。**

## 8. 实验设计

### 8.1 假设

- **H1**：Agent 生成的 diff 中存在可观比例的冗余改动（预期 20%~60%）
- **H2**：最小化后的 diff 仍能通过测试（即最小化不破坏功能）
- **H3**：最小化能显著降低人工 review 成本
- **H4**：在测试失败的场景，致败定位能准确指出问题块

### 8.2 任务集

- 来源：跨多文件的重构 / 特性开发任务
- 规模：20~30 个任务
- 要求：每个任务有**可自动运行的验收测试**（这是判定的前提）
- 记录：每个任务的人工 review 标注（哪些改动是必要的）—— 用于验证算法结论

### 8.3 指标

| 指标 | 定义 | 期望 |
|---|---|---|
| **冗余率** ⭐ | 冗余行数 / 总改动行数 | 报告分布，不是「越高越好」——这是**测量 Agent 质量**的指标 |
| **最小化保真度** | 最小化后测试通过率 | 应 = 100%（否则算法破坏了功能） |
| **定位准确率** | 与人工标注的一致性 | 统计准确率 |
| **判定次数** | 实际测试运行次数 | 观察搜索效率 |
| **耗时** | 端到端时长 | 观察工程可行性 |

### 8.4 成功 / 失败判据

**成功**：
- 最小化保真度 = 100%
- 冗余率测量稳定（同一任务多次运行方差小）
- 在 15 分钟预算内收敛的任务 ≥ 80%

**失败**：
- 保真度 < 100%（说明算法会破坏功能，**必须修**）
- 收敛率 < 50%（说明工程成本过高，需要 §6.1 的影响面优化）
- 同一任务多次运行的冗余率方差异常大（说明 flaky 未处理干净）

### 8.5 这个实验最有价值的产出

> **冗余率是一个「可证明」的评测维度。**

现有评测只回答「任务完成了吗」。本设计额外回答「**完成得干不干净**」。

**与已有研究的区别（重要）**：TRIM 等工作也在度量过编辑，但多用**启发式**（行数、编辑次数、LLM 判断）。
本设计的冗余定义是**可证明的** —— 用测试做 oracle，「移除后验收测试仍通过」才算冗余。

这意味着即使最小化算法本身不完美，**它产出的指标仍然有严格定义**——这是一个「即使失败也有产出」的设计。

## 9. 风险与回退

| 风险 | 严重度 | 缓解 |
|---|---|---|
| 测试太慢，搜索跑不完 | 🔴 高 | §6.1 影响面缩范围；降级为路径匹配；`max_test_runs` 上限 |
| flaky 测试破坏判定 | 🔴 高 | §6.2 预筛 + 重试 |
| 耦合改动导致误判 | 🟠 中 | §3 一致性组 |
| 最小化误删必要改动 | 🟠 中 | 保真度校验（最小化后必须仍 pass） |
| 结果非全局最优 | 🟡 低 | 报告中标注 `converged` |
| 非 git 仓库性能差 | 🟡 低 | 降级复制目录 |

**回退路径**：本工具是**离线、只读**的——它不改 Agent 的行为，只产报告。因此**零风险**，出问题直接不用即可。

## 10. 实施计划

| 阶段 | 时间 | 交付 | 验收 |
|---|---|---|---|
| **P0** | 1 天 | diff 切分 + worktree 隔离 + 跑通「应用/回退子集」 | 能对任意 diff 做子集应用 |
| **P1** | 2 天 | 可编译性检查 + 一致性组构造 | 耦合改动能正确合并 |
| **P2** | 2~3 天 | ddmin 搜索（必要性 + 致败两个方向） | 单任务能跑出结果 |
| **P3** | 1~2 天 | 测试范围缩窄（影响面 or 路径匹配）+ flaky 预筛 | 单任务 15 分钟内收敛 |
| **P4** | 2 天 | 任务集 + 出数字 | 拿到冗余率分布 |

**总计约 1.5~2 周。**

**若只有 1 周**：P0 + P2（不做一致性组，接受部分误判）+ P4 缩小到 10 个任务。产出仍是「冗余率」这个新指标。

## 11. 面试要点

**Q1：这和普通的最小化/reduce 工具有什么区别？**
→ 那些是缩小**触发失败的输入**。这里缩小的是 **Agent 生成的代码改动**，判定是「测试是否通过」，而且分两个方向（必要性最小化 / 致败定位）。

**Q2：为什么不能直接看 diff 判断哪些是多余的？**
→ 因为「多余」的定义是「删掉它功能仍然正确」——这是**语义属性**，不是文本属性。只能靠执行来判定。

**Q3：最难的工程问题是什么？**
→ 两个：① **耦合改动**——改签名和改调用点必须同进同退，按 hunk 独立回退会误判，所以需要「一致性组」；② **测试速度**——朴素做法要跑几百次测试，必须用影响面分析把每次测试的范围缩到最小。

**Q4：flaky 测试怎么办？**
→ 最小化前先对基线跑 3 次，结果不一致的测试从判定集合排除，并在报告里注明。

**Q5：如果 Agent 的改动全都必要呢？**
→ 输出 `redundancy_ratio = 0`。这本身是有信息的——说明这次 Agent 改得很干净。

**Q6：这个工具最大的价值是什么？**
→ 三层：① 减少人工 review 负担；② 测试失败时直接定位到块；③ 产出**可证明的**冗余率指标——第三层即使算法不完美也成立。

**Q6b：TRIM 和 over-editing 这类工作不是已经做了吗？**
→ 是，过编辑已有研究（TRIM 用轨迹最小化、有 over-editing 度量工具）。**本设计的差异有两点**：① 冗余的判定是**可证明的**（测试做 oracle），而它们多用启发式度量；② 用代码结构图做一致性组 + 影响面选测试，把大仓库上跑不动的工程问题解决了。**不要说"这是首创"。**

**Q7：和 Constraint Guard 的关系？**
→ Guard 是事前预防（不许越界），Reducer 是事后清理（越界了也能查出来）。一个减少发生，一个兜底。**两者共用同一套「一致性组 / 影响面」基础设施。**

## 附：术语表

| 术语 | 含义 |
|---|---|
| **hunk** | diff 中的一块连续改动（`@@` 分隔） |
| **一致性组** | 必须同进同退的改动集合，缺少任一成员则项目不可编译 |
| **必要性最小化** | 求最小通过集，找出冗余改动 |
| **致败定位** | 求最小失败集，找出导致测试挂掉的改动 |
| **保真度** | 最小化后功能仍正确的比例 |
| **冗余率** | 冗余改动行数 / 总改动行数（用测试 oracle 定义，可证明） |
| **收敛** | 搜索在预算内到达稳定解 |
