# EVAL —— 统一评测设计

> 解决四个空白：**任务集从哪来**、**指标怎么定义才可比**、**什么时候该停**、**改进怎么验证**

---

## 0. 一句话

> 没有 go/no-go gate 的实验计划等于赌博；没有改进闭环的归因等于白做。
> 本文档定义**怎么测、什么时候停、改完怎么验证**。

---

## 1. 任务集来源方案

### 1.1 三个候选来源

| 来源 | 做法 | 优点 | 缺点 | 采用 |
|---|---|---|---|---|
| **A. 开源仓库真实 commit 反向构造** | 取 `commit^` 作起始快照，用 commit message 改写成任务描述 | 最真实；天然带验收测试 | 需要筛选 commit | ✅ **主体** |
| **B. 从 SWE-bench 类数据集抽取** | 直接用现成任务 | 格式统一 | 仓库过大；**可能已被模型见过（数据污染）** | ❌ |
| **C. 自己构造** | 手写任务 + 测试 | 可控，能精确设计约束 | 成本高；真实性差 | ✅ **补充** |

**决定：A 为主体（约 80%），C 补充特定场景（约 20%），不用 B。**

**不用 B 的理由**：数据污染会让结果失去意义——模型可能"见过"这些任务的答案。这一点必须在文档里明确，面试也会问。

### 1.2 来源 A 的构造流程

**第 1 步：选仓库**

| 条件 | 理由 |
|---|---|
| Python 项目 | 与 pyright 匹配 |
| 有测试目录且覆盖率较高 | 验收测试可得 |
| 中小型（1k~20k 行） | 保证 15 轮内能完成 |
| 活跃维护 | 避免依赖腐烂 |

候选：`click`、`attrs`、`tenacity`、`rich`（部分模块）、`httpx`（部分）

**第 2 步：筛 commit**

筛选条件：

- [ ] 修改 ≥3 个文件
- [ ] 包含测试改动
- [ ] commit message 描述清晰（不是 "fix bug" 这种）
- [ ] 不涉及大范围重命名（会破坏任务描述的可读性）
- [ ] 不涉及外部依赖变更

**第 3 步：构造任务目录**

```
tasks/A-007-<slug>/
├── repo/             # git checkout <commit>^ 的快照（.git 可保留）
├── task.md           # 任务描述
├── tests/            # 该 commit 引入/修改的测试
├── meta.json         # 元数据
└── ground_truth.diff # 原始 commit 的 diff（仅用于分析，不给 Agent）
```

**第 4 步：写 task.md（关键）**

⚠️ **必须删掉实现细节，只留目标。**

```
✅ 好的任务描述：
"现在 X 函数在遇到 Y 情况时会抛出 Z 异常，改为返回 None，
 并同步更新所有调用方。"

❌ 坏的任务描述：
"在 parser.py 第 45 行加上 if not x: return None，
 然后修改 utils.py 的调用点……"
```

**泄露实现方式会让任务变成"抄写"，测不出 Agent 的真实能力。**

**第 5 步：验收测试**

`tests/` 来自原始 commit。判定方式：

```bash
pytest tests/ -q
# 全绿 → pass
```

**必须验证**：`repo/` 原始状态下这些测试是**失败**的（否则这个任务没有区分度）。

### 1.3 来源 C：补充场景

只用来源 A 会缺两类关键任务：

**① 诱导越界任务（Guard 专用）**

设计：任务所需信息在约束允许范围**之外**。

```
约束：只允许修改 src/parser/ 下的文件
任务：实现 X 功能（需要用到 src/utils/helper.py 里的某个函数）
```

**这考验 Agent 会不会越界去改。** 这是 Guard 实验的核心素材，来源 A 里很难找到。

**② 高冗余任务（Diff Reducer 专用）**

设计：任务本身很小，但很容易引来大量"顺手改动"。

```
任务：修复 A 函数的一个边界 bug
陷阱：代码里有若干风格不一致处、"TODO"、可优化点
```

**观测 Agent 会不会顺手改一堆无关的东西。**

### 1.4 任务集规模与配比

| 类别 | 数量 | 服务于 |
|---|---|---|
| 跨文件特性开发（来源 A） | 12 | 全部能力 |
| 跨文件重构（来源 A） | 8 | 全部能力 |
| 诱导越界（来源 C） | 6 | **Guard** |
| 高冗余（来源 C） | 4 | **Diff Reducer** |
| **合计** | **30** | |

**同时要求**：每个任务预期 ≥15 轮、改动 ≥80 行、涉及 ≥5 个文件。

### 1.5 调优集与留出集（防过拟合）

| 集合 | 数量 | 用途 |
|---|---|---|
| **调优集 (dev)** | 20 | 用于归因、指导改进、调参 |
| **留出集 (holdout)** | 10 | **只用于最终验证，不得用于指导改进** |

> **没有留出集，最终数字只能说明"你在测试集上过拟合了"。** 这是必须的。

## 2. 统一指标定义

### 2.1 指标表

| 指标 | 定义 | 归一化 | 服务于 |
|---|---|---|---|
| **任务完成率** | `pass 任务数 / 总任务数` | ✅ 比率 | 全部（硬约束） |
| **总 token 消耗** | 单任务累计（跨组取中位数） | ⚠️ 绝对值，需配对比较 | Context Paging |
| **重复读取率** | `R_waste / R` | ✅ 比率 | Context Paging |
| **约束违反次数** | 绝对次数 | ⚠️ 需除以总轮数 | Guard |
| **约束保持率** ⭐ | 见 §2.2 | ✅ **已修复跨任务不可比** | Guard |
| **冗余率** | `冗余改动行数 / 总改动行数` | ✅ 比率 | Diff Reducer |
| **致败定位准确率** | 与人工标注一致率 | ✅ 比率 | Diff Reducer |
| **归因准确率** | 与人工标注一致率 | ✅ 比率 | Attribution |

### 2.2 约束保持率的定义（修正原缺陷）

**原问题**：若约束从未被违反，存活轮数 = `T + 1`。但不同任务的 `T` 不同（有的 15 轮，有的 40 轮），**15 轮未违反 ≠ 40 轮未违反**，跨任务不可比。

**修正定义**：

```
存活轮数 s = 首次违反发生在第几轮；从未违反则 s = T + 1
约束保持率 ρ = min(s, T) / T          ∈ (0, 1]
```

| 情况 | ρ |
|---|---|
| 从未违反 | `min(T+1, T) / T = 1.0` |
| 第 1 轮就违反 | `1 / T`（接近 0） |
| 第 T/2 轮违反 | `0.5` |

**跨任务聚合用 ρ 的中位数**，而不是存活轮数的平均。

**同时报告两个数**：ρ（归一化，可跨任务比）与 s（绝对，直观）。

### 2.3 为什么用中位数而不是均值

任务难度分布不均，个别极端任务（超长或超短）会严重拉偏均值。**中位数 + 四分位距更能反映典型情况。**

### 2.4 定义中必须明确的边界

| 术语 | 精确定义 |
|---|---|
| `R`（读取次数） | `read_file` 完整读取的次数；`recall` 按符号取**不计入** |
| `R_waste` | 状态表已有最新内容且 `fresh` 时的读取 |
| 冗余改动 | 从 diff 中移除后验收测试仍通过的改动 |
| 致败改动 | 从 diff 中移除后验收测试由 fail 变 pass 的改动 |
| 归因正确 | 与人工标注的 `primary` 分类一致 |

## 3. 对照组矩阵

### 3.1 两级对照

**第一级：增量对照**（证明每个能力有增量）

| 组 | 配置 |
|---|---|
| **A** | 裸 Agent |
| **B** | A + Context Paging |
| **C** | A + Constraint Guard |
| **D** | A + Diff Reducer |
| **E** | **全部启用** |

**第二级：朴素对照**（证明「结构化」优于「文本匹配」）

| 组 | 配置 | 对照对象 |
|---|---|---|
| **B′** | A + 文件状态表但**无符号索引**（只外置全文） | B |
| **C′** | A + **文本层面**约束检查（正则匹配路径，无结构信息） | C |
| **A′** | A + 提示词叮嘱（「不要重复读」「不要越界」） | 全部 |

> **A′ 是最重要的对照** —— 它代表"什么都不做，只在 prompt 里叮嘱"，也就是现状做法。
> **如果 E 不比 A′ 好，整个项目就没有价值。**

### 3.2 为什么两级都要

- 只有第一级 → 无法区分"是机制有效"还是"只是多花了算力"
- 只有第二级 → 无法证明整体价值

### 3.3 注意：不是所有组都要跑全部任务

| 组 | 跑哪些任务 |
|---|---|
| A, B, B′, A′ | 全部 30 个 |
| C, C′ | 全部 30 个（Guard 需要所有任务） |
| D | 只需 20 个改动量大的 |
| E | 全部 30 个 |

**按需裁剪可以省下大量算力。**

## 4. Go / No-Go Gates

> **这一节回答"什么时候该停"。没有它，8 周的计划可能在第 2 周就该放弃了却还在硬做。**

### Gate 0（Day 1~3）：基线可行性 ⭐ 最重要

**测什么**：现状下 `R_waste / R`、压缩触发频率、约束违反情况

| 条件 | 判定 | 行动 |
|---|---|---|
| 重复读取率 > 15% | ✅ 通过 | 继续 S2（Context Paging） |
| 重复读取率 5%~15% | ⚠️ 边际 | 缩小 S2 范围，或跳到 S4（Diff Reducer） |
| 重复读取率 < 5% | ❌ **不通过** | **停止 Context Paging**，省下 2 周 |

**这是唯一能在 3 天内否掉一个 2 周工作的 gate，必须先做。**

### Gate 1（S1 后）：符号解析质量

| 条件 | 判定 |
|---|---|
| Precision ≥ 0.90 **且** Recall ≥ 0.85 | ✅ 进入 S2 |
| 任一项不达标 | ❌ 先修 LSP 集成，**不进入 S2** |

### Gate 2（S2 后）：Context Paging 效果

| 条件 | 判定 |
|---|---|
| token 下降 ≥ 20% **且** 完成率下降 ≤ 2% | ✅ 保留该能力 |
| token 下降 < 10% | ⚠️ 分析：是索引开销过大还是 Agent 没用起来 |
| 完成率下降 > 5% | ❌ 回退到 A′ 配置，记录失败原因 |

### Gate 3（S3 后）：影响面可用性

| 条件 | 判定 |
|---|---|
| 影响面查询 P95 延迟 < 2s | ✅ 进入 S4/S5 |
| 延迟过高 | ⚠️ 加缓存；否则 S4 降级为路径匹配 |

### Gate 4（S4 后）：Diff Reducer 有效性

| 条件 | 判定 |
|---|---|
| 最小化保真度 = 100% **且** 15 分钟内收敛率 ≥ 80% | ✅ 保留 |
| 保真度 < 100% | ❌ **必须修**（算法会破坏功能） |
| 收敛率 < 50% | ⚠️ 依赖 S3 的影响面优化；否则缩小任务规模 |

### Gate 5（S5 后）：Guard 效果

| 条件 | 判定 |
|---|---|
| 约束保持率显著高于 A′ **且** 完成率下降 ≤ 2% | ✅ 保留，`warn` 升为 `rollback` |
| 完成率下降 > 5% | ❌ 约束过严，回退到 `warn` 模式并收窄约束范围 |
| E 与 C′ 无差异 | ⚠️ 说明结构信息没带来增量，**结论要相应改写** |

### Gate 6（S6 后）：归因准确性

| 条件 | 判定 |
|---|---|
| 准确率显著高于随机（9 类随机 ≈ 11%） | ✅ 保留 |
| 接近随机 | ❌ 分类体系或信号表有问题，回到 `ATTRIBUTION.md` §6 迭代 |
| `unknown` 占比 > 40% | ⚠️ 信号覆盖不足，补埋点 |

## 5. 改进闭环

> **这是原设计缺失的一环。没有它，"归因指导改进"只是一句话。**

### 5.1 闭环流程

```
① 基线测量（Gate 0）
        ↓
② 跑调优集（20 个任务），收集失败样本
        ↓
③ 归因（ATTRIBUTION）→ 得到失败构成分布
        ↓
④ 按占比排序，选最大的那一类
        ↓
⑤ 针对性改进
   planning       → 改规划提示词 / 加 plan 校验
   context_missing→ 实现 Context Paging
   constraint_drift→ 实现 Constraint Guard
   thrashing      → 实现 Diff Reducer 的致败定位
   tool_use       → 改工具描述
   capability     → 换模型
   environment    → 修环境（非 Agent 问题）
        ↓
⑥ 重测【同一调优集】
        ↓
⑦ 验证：该类占比是否下降？总完成率是否上升？
   ├─ 是 → 闭环成立，记录改进项
   └─ 否 → 归因错误 或 改进方向错 → 回到 ③ 复核
        ↓
⑧ 全部改进完成后，在【留出集】上做最终验证
```

### 5.2 关键约束

| 约束 | 理由 |
|---|---|
| **改进必须用同一任务集重测** | 控制变量 |
| **留出集不得用于指导改进** | 防止过拟合 |
| **每轮改进只改一个变量** | 否则无法归因 |
| **改进后完成率下降 → 撤销该改进** | 防止局部优化伤害整体 |

### 5.3 闭环成功判据

**闭环成立** = 至少完成一轮「归因 → 改进 → 重测 → 该分类占比下降」。

**这本身就是一个可报告的结果**，即使最终数字不惊艳：

> "我做了 3 轮归因-改进循环，`context_missing` 从占比 34% 降到 11%。"

## 6. 显著性与统计

> **样本量小（30 个任务），必须诚实处理统计问题。**

### 6.1 诚实的前提

| 事实 | 含义 |
|---|---|
| n = 30（留出集 10） | **统计功效低，只能检测大效应** |
| 任务难度分布不均 | 均值不可靠，用中位数 |
| 非确定性（LLM 采样） | 单次结果不可信，需多次运行 |

### 6.2 做法

| 项目 | 做法 |
|---|---|
| **实验设计** | **配对**（同一任务在所有组跑，比较配对差） |
| **检验方法** | Wilcoxon signed-rank（非参数，不假设正态） |
| **效应量** | 报告 Cliff's delta 或中位数差 + 四分位距 |
| **置信区间** | Bootstrap（1000 次重采样） |
| **重复次数** | 每组每任务跑 **3 次**，取中位数 |

### 6.3 报告口径（必须写清）

**能否宣称"显著"？**

- ✅ 若效应量大（Cliff's delta > 0.47）且 p < 0.05 → 可称"在该任务集上观察到显著差异"
- ⚠️ 若效应量小但方向一致 → 只能说"观察到趋势，样本量不足以确认"
- ❌ **不宣称 p < 0.05 就等于"普遍有效"** —— 结论限于本任务集，不外推

**这段口径要写进报告**，面试被问到时照实说。

## 7. 执行流程与算力预算

### 7.1 跑分矩阵

| 组 | 任务数 | 重复 | 总运行数 |
|---|---|---|---|
| A | 30 | 3 | 90 |
| A′ | 30 | 3 | 90 |
| B | 30 | 3 | 90 |
| B′ | 30 | 3 | 90 |
| C | 30 | 3 | 90 |
| C′ | 30 | 3 | 90 |
| D | 20 | 3 | 60 |
| E | 30 | 3 | 90 |
| **合计** | | | **690 次** |

### 7.2 算力估算

假设单次运行 8 分钟（含测试）：

```
690 × 8 分钟 ≈ 92 小时 ≈ 3.8 天（串行）
```

**并行 4 路 → 约 1 天。**

**这是必须提前规划的资源**，否则到最后发现跑不完。

### 7.3 成本控制

| 手段 | 说明 |
|---|---|
| **分层跑** | 先跑 Gate 0（只跑 A 组 30 个任务 × 1 次 = 30 runs） |
| **按需裁剪** | D 组只跑 20 个任务 |
| **早停** | 任务超过轮次上限即终止，计入 fail |
| **缓存** | 相同配置的测试结果复用 |

### 7.4 数据完整性要求

每次运行必须记录（缺一不可）：

```
attempt_id, task_id, config, run_index,
start/end time, turns, tokens,
all agent_events, final diff,
test result, gate metrics
```

**缺了轨迹就无法归因，必须重跑。**

## 8. 风险

| 风险 | 严重度 | 缓解 |
|---|---|---|
| **任务集造不出来** | 🔴 高 | 先用 3 个任务跑通全流程，再批量造 |
| **算力不够** | 🟠 中 | 分层跑；先跑 Gate 0；并行 |
| **数据污染**（模型见过任务） | 🟠 中 | 不用 SWE-bench；用较新 commit |
| **过拟合测试集** | 🟠 中 | 调优集/留出集分离 |
| **样本量不足** | 🟠 中 | 如实报告效应量，不强称显著 |
| **非确定性导致方差大** | 🟠 中 | 每组跑 3 次取中位数 |
| **某个 gate 不通过** | 🟡 低 | 已定义每个 gate 的后续动作 |

## 9. 面试要点

**Q1：任务集哪来的？**
→ 主体是从开源仓库真实 commit 反向构造（取 `commit^` 作起始快照，把 commit message 改写成任务描述，用该 commit 的测试做验收）。另补充两类自造任务：**诱导越界**（Guard 需要）和**高冗余**（Diff Reducer 需要）。**故意不用 SWE-bench——数据污染会让结果失去意义。**

**Q2：怎么保证任务描述不泄露答案？**
→ 写任务描述时删掉所有实现细节，只留目标。而且有一个反向验证：起始快照下验收测试必须是失败的，否则这个任务没有区分度。

**Q3：30 个任务够做统计吗？**
→ 不够做强统计结论，所以我用**配对设计 + 非参数检验 + 报告效应量**，不宣称"显著就等于普遍有效"。结论严格限定在这个任务集上。

**Q4：怎么防止过拟合测试集？**
→ 分调优集（20 个）和留出集（10 个）。归因和改进只用调优集，**留出集只在最后验证一次**。

**Q5：如果做完发现没效果怎么办？**
→ 每个阶段都有 gate。最关键的是 **Gate 0（3 天）**——先测现状的重复读取率，如果 <5%，直接砍掉 Context Paging 省下 2 周。**先花 3 天验证核心假设，比做完 8 周才发现没效果强。**

**Q6：怎么证明有效不是"多花了算力"？**
→ 设了两级对照。第一级是增量对照（A/B/C/D/E），第二级是**朴素对照**（B′ 无符号索引、C′ 文本检查、A′ 只在提示词里叮嘱）。**A′ 最关键——它代表现状做法。如果 E 不比 A′ 好，项目就没有价值。**

**Q7：归因做完了怎么知道有没有用？**
→ 有改进闭环：归因 → 挑占比最大的一类 → 针对性改进 → 同一任务集重测 → 看该类占比是否下降。**我做了 N 轮循环，`context_missing` 从 34% 降到 11%** —— 这个结论本身就是成果。
