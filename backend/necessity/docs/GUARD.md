# Constraint Guard —— 结构感知的约束保持系统

> 设计文档 v1
> 目标：把任务约束编译成**确定性检查器**，每一轮验证，越界即拦截/回滚

---

## 0. 一页摘要

**问题**：Agent 在长任务中会「约束漂移」——前几轮遵守「只改 parser 目录」，第 N 轮开始改别的文件。已有记录：子 Agent 无视 "surgical edits only" 指令、Cursor 修改用户没让它改的文件。学术界称之为 **Constraint Decay**。

**现有解法全都在用代理指标猜**（同一文件改了几次、diff 超过多少行），**没有人用代码的结构语义来判断**。而「这条约束违反了没有」本质上是结构问题。

**方案**：约束编译成结构化检查器 → 每轮预检 + 后检 → 违反即拦截/回滚。

**核心指标**：**约束保持率 ρ** = `min(存活轮数, 总轮数) / 总轮数`（归一化，跨任务可比；定义见 §1.2）。

---

## 1. 问题定义

### 1.1 可度量的现象

令一次任务有约束集 `C = {c₁, ..., cₖ}`，任务执行 `T` 轮。

| 指标 | 定义 | 可比性 |
|---|---|---|
| **约束违反次数** | `Σ violations(cᵢ)` | ⚠️ 绝对值，跨任务不可比 |
| **每轮违反率** | 违反次数 / `T` | ✅ |
| **约束保持率 ρ** ⭐ | 见 §1.2 | ✅ **已归一化** |
| **越界改动行数** | 违反约束的改动行数总和 | ⚠️ 需除以总改动行数 |

#### 1.2 约束保持率（修正原指标缺陷）

**原定义的错误**：早期直接用「存活轮数 = 首次违反发生的轮次，无违反则 `T+1`」。

**问题**：不同任务的 `T` 不同（有的 15 轮，有的 40 轮）。

> **15 轮未违反 ≠ 40 轮未违反** —— 存活轮数跨任务不可比，无法聚合。

**修正定义**：

```
存活轮数 s = 首次违反发生在第几轮；从未违反则 s = T + 1
约束保持率 ρ = min(s, T) / T          ∈ (0, 1]
```

| 情况 | ρ |
|---|---|
| 从未违反 | `min(T+1, T) / T = 1.0` |
| 第 1 轮就违反 | `1 / T`（接近 0） |
| 第 T/2 轮违反 | `≈ 0.5` |

**跨任务聚合用 ρ 的中位数**（不用均值——任务长度分布不均，均值易被极端值拉偏）。

**报告时同时给出两个数**：`ρ`（归一化，用于跨任务比较）与 `s`（绝对值，用于直观描述）。

> 与 `EVAL.md` §2.2 保持一致。**两份文档的指标定义必须同源。**

### 1.2 已有记录的现象

| 来源 | 现象 |
|---|---|
| Claude Code Issue #63356 | 子 Agent 无视 "surgical edits only"，过度编辑配置文件 |
| Cursor 论坛 | Agent 持续修改用户未指定的文件（有人为此写了 MCP 审计器） |
| vibe-coding-anti-patterns | 收录为反模式 `refactor-scope-creep` |
| 论文 *Constraint Decay* | 长任务中 Agent 逐渐违反初始约束 |

### 1.3 为什么提示词解决不了

**因为提示词本身会被稀释。**

```
第 1 轮：约束在上下文最前面，权重高 → 遵守
第 10 轮：约束被挤到很后面，中间插了几十个工具结果 → 权重下降
第 20 轮：上下文被压缩，约束只剩一句摘要 → 基本失效
```

**约束衰减的根因是上下文的物理特性，不是模型「不听话」。**

## 2. 约束的形式化

### 2.1 三元组定义

一条约束 `c = (scope, predicate, phase)`

| 元素 | 含义 | 例 |
|---|---|---|
| **scope** | 约束作用的对象集合 | 「`src/parser/` 下的文件」 |
| **predicate** | 必须成立的条件 | 「改动只发生在 scope 内」 |
| **phase** | 检查时机 | `pre` / `post` / `both` |

### 2.2 典型约束的结构化表示

```json
{
  "id": "c1",
  "type": "file_scope",
  "scope": {"kind": "path_glob", "patterns": ["src/parser/**"]},
  "predicate": {"kind": "allowlist"},
  "phase": "both",
  "on_violation": "rollback",
  "message": "只允许修改 src/parser/ 下的文件"
}
```

## 3. 可机器验证的边界（设计关键）

> **这一节定义了系统的能力边界。含糊的约束必须被明确拒绝，而不是假装能验证。**

### 3.1 可验证的约束类型

| 类型 | 例 | 验证方式 | 需要的基础设施 |
|---|---|---|---|
| `file_scope` | 只准改 `src/parser/**` | 路径匹配 | 文件树 |
| `symbol_scope` | 只准改非 public 符号 | 可见性分析 | documentSymbol |
| `signature_stable` | `parse()` 签名不变 | 前后签名对比 | documentSymbol |
| `call_chain` | 只准改 `main()` 可达的符号 | 图上可达性 | **调用图** |
| `impact_limit` | 影响面不超过 N 个文件 | 影响面计算 | **调用图** |
| `dependency_frozen` | 不新增第三方依赖 | manifest / import 差分 | import 解析 |
| `test_preserved` | 指定测试必须仍通过 | 跑测试 | 测试运行器 |
| `size_limit` | 改动不超过 N 行 | diff 统计 | diff |

### 3.2 不可验证的约束（必须明确拒绝）

| 例 | 为什么不可验证 |
|---|---|
| 「代码要优雅」 | 无客观谓词 |
| 「不要破坏现有功能」 | 需要操作化为具体测试，否则无定义 |
| 「尽量少改」 | 「尽量」无阈值 → 拒绝；若改为「不超过 50 行」则可验证 |
| 「保持代码风格一致」 | 除非能给出可执行的风格检查器 |

### 3.3 拒绝机制

编译阶段遇到不可验证的约束时：

```
✗ 约束不可验证：第 3 条
  "代码要写得优雅一些"
  原因：无法编译为确定性谓词
  建议：改为可验证的形式，例如「不新增超过 20 行」或「通过 ruff 检查」
```

**绝不允许静默忽略** —— 否则用户以为有这条约束的保护，实际没有。这比不设约束更危险。

## 4. 约束编译器

### 4.1 核心设计决策：**编译用 LLM，验证不用**

| 阶段 | 用什么 | 理由 |
|---|---|---|
| 编译（自然语言 → 结构化） | ✅ 可以用 LLM | 一次性、容错、便宜；错了用户能看出来 |
| **验证（每轮检查）** | ❌ **必须是确定性代码** | 每轮都要跑；必须可复现、快、不可被绕过 |

**为什么验证绝不能用 LLM**：

1. **不可复现** —— 同一输入两次结果可能不同 → 指标失去意义
2. **慢且贵** —— 每轮都要跑
3. **可被绕过** —— Agent 可以说服裁判
4. **无法解释** —— 「为什么判我违反」说不清

### 4.2 编译流程

```
自然语言约束
    ↓
[LLM 编译] → 候选结构化约束 + 类型标注
    ↓
[校验] → type 是否在可验证清单内？
    ↓ 不在 → 拒绝 + 给出改写建议
    ↓ 在
[冲突检测] → 与其他约束是否互斥 / 不可满足？
    ↓ 有冲突 → 报错，要求用户澄清
    ↓ 无
[用户确认] → 展示编译结果，用户可修改
    ↓
结构化约束集
```

**用户确认这一步是必须的** —— LLM 编译可能理解偏，人确认一次成本很低，但能避免整轮跑偏。

### 4.3 冲突检测

| 冲突类型 | 例 | 检测方式 |
|---|---|---|
| 互斥 | 「只改 A」+「必须改 B」 | scope 交集为空但 predicate 都要求成立 |
| 不可满足 | 「只改 A」+「必须通过只在 B 中的测试」 | 预跑一次验证 |
| 循环依赖 | 「改 A 前必须先改 B」+「改 B 前必须先改 A」 | 依赖图找环 |

## 5. 预检 vs 后检

### 5.1 职责划分

| | **预检 (pre)** | **后检 (post)** |
|---|---|---|
| 时机 | 工具调用执行**前** | 改动落地**后** |
| 输入 | 工具名 + 参数（**意图**） | 实际 diff（**结果**） |
| 能力 | 拦截（不执行） | 回滚 |
| 精度 | 低 | 高 |
| 成本 | 低 | 中 |

### 5.2 为什么两者都要

**预检看意图，可能漏。**

例：Agent 调用 `shell_command("python fix.py")`，意图上看不出会改什么文件；预检无法判断。但脚本跑完可能改了 `src/utils.py`。

**后检看结果，最权威。**

```
预检（快，拦明显越界）
   ↓ 通过
执行
   ↓
后检（权威，看实际结果）
   ↓ 违反 → 回滚
```

**预检的价值是省一次执行成本 + 早点告诉 Agent 方向错了；后检的价值是兜底正确性。**

### 5.3 后检怎么拿到「实际 diff」

> **原文档只说了"要扫描工作区"，但没定义怎么扫、扫多频繁、多快算快。本节补齐。**

#### 5.3.1 三档扫描机制（按可用性降级）

| 档 | 机制 | 成本 | 适用 |
|---|---|---|---|
| **L1（首选）** | `git status --porcelain=v1 -z` + `git diff --numstat` | **毫秒级** | 是 git 仓库 |
| **L2** | 自维护元数据树 `path → (size, mtime, hash)`，遍历比对 | 与文件数线性 | 非 git 仓库 |
| **L3（降级）** | 只扫工具参数声明的路径 | 极低 | L1/L2 都不可用 |

**L3 是不可靠的**（Agent 可通过 `shell_command` 改别的文件），使用时必须在报告中标注 **"检测能力受限"**，且不得用于出实验数字。

#### 5.3.2 扫描时机与性能约束

```
before_tool(call)
    → 记录快照 S_before（L1: git 索引；L2: 元数据树）

    执行工具

after_tool(call, result)
    → 记录快照 S_after
    → Agent 变更 = diff(S_before, S_after)      ← 窗口内 = Agent 引起
```

**关键设计：用「工具调用窗口」界定归因。**

窗口内发生的变化归因于 Agent；窗口外（如 git checkout、外部进程）标记为 `external`，**不计入约束违反**。

| 性能约束 | 阈值 | 超限动作 |
|---|---|---|
| 单次扫描耗时 | > 500 ms | 降级为**每轮扫描一次**（而非每次工具调用） |
| 工作区文件数 | > 50k | 强制 L1；无 git 则降级 L3 并标注 |
| 单次扫描差异文件数 | > 1000 | 疑似非 Agent 引起（如 git 操作）→ 标记 `suspect_bulk`，转 `warn` 不 `rollback` |

#### 5.3.3 排除规则

复用 Aurora 已有的排除表（`tools/file_rw.py:28` 的 `SKIP_DIRS`）：

```
.git/  __pycache__/  node_modules/  .venv/  venv/  .tox/
.mypy_cache/  .pytest_cache/  dist/  build/  .next/  target/
```

**额外排除**（本项目自身产生的文件）：

```
.necessity/          ← 状态表、备份、报告
```

**不排除 `.necessity/` 会导致自我触发**：Guard 写备份 → 检测到文件变化 → 又触发检查 → 无限循环。

#### 5.3.4 大仓库的优化

| 手段 | 说明 |
|---|---|
| **增量元数据树** | 只重算 mtime 变化的条目 |
| **目录级短路** | 目录 mtime 未变则跳过整棵子树 |
| **延迟 hash** | 先比 `(size, mtime)`，只有变了才算 hash |
| **git 优先** | git 已维护索引，比自建树快一个数量级 |

#### 5.3.5 与 diff 内容获取的衔接

扫描只负责**发现哪些文件变了**。需要具体 diff 内容时：

| 档 | 获取方式 |
|---|---|
| L1 | `git diff -- <path>` |
| L2 | 从元数据树取上一版内容（需缓存内容）或 `difflib` 对比 |

**注意**：L2 若要出 diff，必须缓存内容——这会显著增加内存。**实践建议：L2 只报告"文件变了 + 行数变化"，不报告具体 diff 内容**，除非该文件是约束检查的目标。

## 6. 覆盖所有写入路径（安全关键）

> **这是本设计最容易出洞的地方。**

### 6.1 漏洞模式

若约束检查只挂在 `file_write` 工具上：

```
约束：只准改 src/parser/
Agent：shell_command("echo 'x' > src/utils.py")   ← 绕过！
```

**同类漏洞在真实系统中反复出现** —— 例如 Aurora 的审批机制曾只接了 `shell_command`，`file_delete` / `network` / `mcp_tool` / `computer_use` / `code_exec` 全都能绕过。

### 6.2 正确做法：在「文件系统写入」这一层拦截，而不是在工具层

| 方案 | 可靠性 |
|---|---|
| 在每个工具上分别加检查 | ❌ 漏一个就破防 |
| **扫描工作区 diff（后检）** | ✅ **与工具无关，兜底可靠** |
| 文件系统级拦截（inotify / 只读挂载） | ✅ 最可靠，但实现重 |

**推荐：以「工作区 diff 扫描」为主，工具级预检为辅。**

理由：**后检不依赖 Agent 用什么工具**，只要文件变了就能发现。这是与工具无关的兜底。

### 6.3 必须枚举的写入路径

| 路径 | 是否被 diff 扫描覆盖 |
|---|---|
| `file_write` / `apply_patch` | ✅ |
| `shell_command` 里的重定向 / `sed -i` / `mv` | ✅ |
| `code_exec` 执行脚本 | ✅ |
| `computer_use` 模拟编辑 | ✅ |
| `mcp_proxy` 调用的外部工具 | ✅ |
| git 操作（checkout / stash） | ⚠️ 需排除，否则误判 |
| 外部进程并发修改 | ⚠️ 需区分，否则误判 |

**最后两条要特别处理**：git 操作和外部修改不是 Agent 干的，不应算违反。做法：记录操作前后的 git 状态，排除非 Agent 引起的变更。

## 7. 违反处理与反馈

### 7.1 处理策略

| 策略 | 行为 | 适用 |
|---|---|---|
| `block` | 预检拦截，不执行 | 明显越界 |
| `rollback` | 执行后回滚（默认） | 后检发现 |
| `warn` | 只记录 | 观察期 |
| `ask` | 转人工审批 | 高风险改动 |

### 7.2 反馈设计（关键）

拦截时必须告诉 Agent **违反了哪一条、为什么**：

```
✗ 约束违反 [c1: file_scope]
  你修改了 src/utils/helper.py
  但本任务约束为：只允许修改 src/parser/ 下的文件
  该改动已回滚（1 个文件，16 行）

  提示：如需修改该文件，请先确认任务范围是否应扩大。
```

**这句反馈本身就是防约束衰减的手段** —— Agent 不知道自己跑偏了，明确告诉它就能拉回来。

### 7.3 反馈的反效果风险

**如果反馈太频繁，会挤占上下文，反而降低效率。**

缓解：
- 同一约束连续违反时，反馈**合并**而非逐次输出
- 提供 `warn` 模式先观察违反频率，再决定是否启用 `rollback`

## 8. 数据模型

```sql
-- 约束定义（每任务）
CREATE TABLE constraint_spec (
  task_id       TEXT NOT NULL,
  constraint_id TEXT NOT NULL,
  type          TEXT NOT NULL,     -- file_scope | signature_stable | ...
  spec_json     TEXT NOT NULL,     -- 结构化定义
  phase         TEXT NOT NULL,     -- pre | post | both
  on_violation  TEXT NOT NULL,     -- block | rollback | warn | ask
  message       TEXT,
  PRIMARY KEY (task_id, constraint_id)
);

-- 违反日志
CREATE TABLE constraint_violation (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id       TEXT NOT NULL,
  session_id    TEXT NOT NULL,
  turn          INTEGER NOT NULL,      -- 第几轮（用于算存活轮数）
  constraint_id TEXT NOT NULL,
  detected_by   TEXT NOT NULL,         -- precheck | postcheck
  attempted     TEXT,                  -- 意图（工具名+参数摘要）
  actual        TEXT,                  -- 实际结果（改了哪些文件几行）
  handled       TEXT NOT NULL,         -- blocked | rolled_back | warned | asked
  ts            REAL NOT NULL
);

-- 未通过编译的约束（审计用）
CREATE TABLE constraint_rejected (
  task_id     TEXT NOT NULL,
  raw_text    TEXT NOT NULL,
  reason      TEXT NOT NULL,
  suggestion  TEXT
);
```

**`constraint_rejected` 表不是装饰** —— 它让「哪些约束没被保护」变得可见。

## 9. 边界情况与失败模式

| # | 情况 | 处理 |
|---|---|---|
| 1 | 约束编译失败 | 拒绝并给建议；**不静默忽略** |
| 2 | 约束互相冲突 | 编译时检测，要求用户澄清 |
| 3 | 约束不可满足（任务做不完） | 预跑验证；若不可满足，报错 |
| 4 | 约束过严导致完成率暴跌 | **必须在实验中监控**；提供 `warn` 模式做灰度 |
| 5 | git 操作引起大量文件变更 | 排除非 Agent 变更（对比 git 状态） |
| 6 | 外部进程并发改文件 | 同上；无法区分时降级为 `warn` |
| 7 | 检查器自身抛异常 | **放行 + 记录**（不能因检查故障阻塞任务） |
| 8 | 后检回滚失败 | 告警 + 记录，转人工 |
| 9 | 反馈刷屏 | 同约束连续违反时合并反馈 |
| 10 | 约束覆盖不到的场景（如内存中改动后写回） | diff 扫描能捕获，因为最终落盘 |

**总原则（与 Aurora 的 `approval_gate` 一致）：检查系统故障时放行，不阻塞任务。** 但必须记录，以便事后审计。

## 10. 实验设计

### 10.1 假设

- **H1**：不加护栏时，约束在长任务中会衰减（存活轮数显著小于总轮数）
- **H2**：加护栏后，约束存活轮数显著提升
- **H3**：护栏不会显著降低任务完成率
- **H4**：结构验证优于文本验证

### 10.2 对照组（关键）

| 组 | 配置 |
|---|---|
| **A** | 约束只写在系统提示词里（**现状做法**） |
| **B** | 文本层面检查（正则匹配文件路径，无结构信息） |
| **C** | **结构层面检查（本设计）** |

**B 组是核心对照** —— 它隔离出「结构语义」单独的贡献。若 C 不比 B 好，说明用规则匹配就够了，**结论要相应改写**。

### 10.3 任务集要求

- 每个任务有**明确且可机器验证**的约束（如「只准改 src/parser/」）
- 任务足够长（≥15 轮），否则观察不到衰减
- 混入**诱导越界**的设计：任务本身需要的信息在允许范围外（考验 Agent 是否会越界去拿）
- 规模：15~20 个任务

### 10.4 指标

| 指标 | 定义 | 期望 |
|---|---|---|
| **约束保持率 ρ** ⭐ | `min(存活轮数, T) / T`，跨任务取中位数 | C > B > A |
| 约束存活轮数 s | 首次违反发生轮次（绝对值，辅助展示） | C > B > A |
| **约束违反次数** | 总次数 | C < A |
| **越界改动行数** | 违反约束的改动行数 | C 显著低 |
| **任务完成率** | 验收测试 pass 率 | **C ≈ A（下降 ≤2%）** |
| **总轮数** | 任务长度 | 观察：护栏是否让任务变长 |

### 10.5 成功 / 失败判据

**成功**：约束保持率 ρ 显著提升（例如 A 组 ρ 中位数 0.22 → C 组 1.0）**且** 完成率下降 ≤ 2%

**失败**：
- 完成率下降 > 5%（约束过严）
- C 组与 B 组无显著差异（说明结构信息没带来增量）
- 违反次数接近 0 但任务也做不完（说明约束把 Agent 卡死了）

## 11. 风险与回退

| 风险 | 严重度 | 缓解 |
|---|---|---|
| **完成率下降**（约束过严） | 🔴 高 | `warn` 模式灰度；实验中作为硬约束监控 |
| **检查被绕过** | 🔴 高 | §6 以工作区 diff 扫描为主，不依赖工具层 |
| 约束编译错（LLM 理解偏） | 🟠 中 | 用户确认步骤 |
| 反馈刷屏挤占上下文 | 🟠 中 | 合并同约束的连续违反 |
| 检查器故障阻塞任务 | 🟠 中 | 故障时放行 + 记录 |
| git/外部修改误判 | 🟡 低 | 对比 git 状态排除 |

**回退路径**：`guard.enabled = false` 时行为完全等于现状。所有约束默认 `warn`，确认无误后再切 `rollback`。

## 13. 面试要点

**Q1：为什么提示词解决不了？**
→ 提示词本身会被上下文稀释和压缩。**约束衰减的根因是上下文的物理特性，不是模型不听话。**

**Q2：验证为什么不能用 LLM？**
→ 四个理由：不可复现（指标失去意义）、慢且贵、可被 Agent 说服绕过、无法解释。**编译可以用 LLM（一次性），验证必须是确定性代码（每轮跑）。**

**Q3：怎么防止 Agent 绕过检查？**
→ 检查不能挂在工具层。**以工作区 diff 扫描为主**——不管 Agent 用什么工具，文件变了就能发现。这是与工具无关的兜底。

**Q4：约束写得太严导致任务做不完怎么办？**
→ 这是本设计最大的风险。三条缓解：① 默认 `warn` 模式灰度；② 实验中把「完成率不降」设为硬约束；③ 不可满足的约束在编译阶段就检测出来。

**Q5：和 Aurora 里已有的审批机制什么关系？**
→ 审批管的是「危险操作要不要放行」（安全），Guard 管的是「改动是否在任务范围内」（范围）。两者正交，但**共享同一个教训**：检查必须覆盖所有路径，不能只接一个工具。

**Q6：什么约束你不能验证？**
→ 任何无法编译成确定性谓词的，比如「代码要优雅」。**这类必须明确拒绝并给出改写建议，绝不能静默忽略**——否则用户以为有保护，实际没有。

|---|---|
| **约束漂移 / Constraint Decay** | 长任务中 Agent 逐渐违反初始约束 |

| **后检** | 执行后基于实际 diff 的检查 |

| **约束存活轮数 s** | 首次违反发生轮次（绝对值，辅助展示） |
| **确定性验证** | 用代码而非 LLM 做判定 |
| **覆盖所有写入路径** | 检查不能只在工具层，须在工作区层兜底 |
