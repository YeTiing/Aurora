# Necessity —— Agent 改动质量保障系统

> 系统总览 v1
> 统一命题：**现有 Agent 只保证「充分」，本系统同时保证「必要」。**

---

## 0. 一句话

> 现有 Agent 评测只回答「任务完成了吗」——这是**充分性**。
> 本系统回答「完成的过程中，有没有多余的动作」——这是**必要性**。
>
> **充分且必要，才是干净的改动。**

## 1. 为什么是这四个能力

「必要」不是单一属性，它在任务的不同时刻表现为不同问题：

| 时刻 | 违反「必要」的表现 | 对应能力 |
|---|---|---|
| 读上下文时 | 反复重读同一文件，浪费上下文 | **Context Paging** |
| 动手之前 | 改动的范围超出了任务要求 | **Constraint Guard** |
| 动手之后 | diff 里混着多余改动 | **Diff Reducer** |
| 任务失败时 | 只知道挂了，不知道为什么 | **Failure Attribution** |

**四个能力覆盖一条时间线，共享一套基础设施。**

## 2. 基础设施（被四个能力共同依赖）

> **CodeGraph 不是一个"阶段"，是基础设施。** 它在流程中被查询多次。

```
┌─────────────────────────────────────────────────────────┐
│  基础设施（CodeGraph）                                    │
│                                                         │
│  • 符号解析      LSP documentSymbol                      │
│  • 调用图        LSP callHierarchy                      │
│  • 影响面查询    调用图上的可达性 + 测试覆盖反查            │
│  • 文件状态表    内容外置 + 失效判定                       │
└──────┬──────────────┬──────────────┬──────────────┬─────┘
       │              │              │              │
       ▼              ▼              ▼              ▼
  Context        Constraint      Diff         Failure
  Paging           Guard        Reducer      Attribution
  (只需符号解析)   (需调用图)    (需影响面)    (需轨迹+证据)
```

**依赖强度**：

| 能力 | 依赖 | 可降级 |
|---|---|---|
| Context Paging | 符号解析 | ✅ 无符号索引时只存全文 |
| Diff Reducer | 影响面（用于缩小测试范围） | ✅ 降级为路径匹配 |
| Constraint Guard | 调用图（用于调用链约束） | ✅ 不做调用链类约束 |
| Failure Attribution | 轨迹 + 上述所有信号 | ✅ 只用规则 |

**没有一个是硬依赖**——每个都有降级路径。这保证了可以增量交付。

## 3. 端到端时序（一个任务里它们何时被调用）

```
任务：「把 parse() 改成支持异步」
│
├─ ① 开始，读文件
│     └─ Context Paging：返回符号索引，不返回全文
│        状态表建立，压缩碰不到它
│
├─ ② 动手前探路
│     ├─ CodeGraph.impact("parse")   → 12 个调用方，3 个测试文件
│     └─ Constraint Guard.precheck() → 本次改动是否越界？
│
├─ ③ Agent 改代码（多轮）
│     ├─ Context Paging.recall(symbol="parse")  → 按符号取，不整读
│     ├─ Constraint Guard.postcheck(diff)       → 每轮后检，越界即回滚
│     └─ Context Paging.mark_dirty(path)        → 自己改的不重读
│
├─ ④ 改完跑测试
│     └─ CodeGraph.tests_for_impact()  → 只跑受影响的 3 个测试
│                                         （全量 30s → 子集 2s）
│
├─ ⑤ 若测试失败
│     └─ Diff Reducer.locate()   → 二分定位致败块
│
├─ ⑥ 收尾
│     ├─ Diff Reducer.minimize()      → 最小 diff + 冗余率
│     ├─ Constraint Guard.report()    → 约束存活轮数、违反次数
│     └─ Failure Attribution.attribute()  → 若失败，归因并分类
│
└─ ⑦ 全局
      └─ CodeGraph 全程提供结构查询（被查 ≥3 次）
```

## 4. 模块划分

> **权威定义在 `INTEGRATION.md` §2。** 本节只给概览，避免两处不一致。

```
backend/necessity/   # Necessity 已合并进 Aurora（完整树见 INTEGRATION.md §2）
├── hooks.py         #   钩子契约（宿主与 core 的唯一交互面）
├── capability.py    #   能力装配（CompositeHooks）
├── adapter.py       #   宿主接入面（原 adapter/aurora，宿主即本仓库）
│
├── index/           #   基础设施：符号 / 调用图 / 影响面 / 存储 / 轨迹
├── context/         #   能力 1：Context Paging
├── guard/           #   能力 2：Constraint Guard
├── reduce/          #   能力 3：Diff Reducer
├── attribution/     #   能力 4：Failure Attribution
│
├── mcp/             # MCP Server（仅 Reduce / Attribution / Context 可 MCP 化）
├── cli/             # 离线命令行
├── eval/            # 评测：任务集 / 跑分 / 报告
└── docs/            # 本套设计文档

⚠️ LSP 传输层**不在本包内** —— 统一使用 `backend/lsp/`（详见 INTEGRATION.md §2）。
```

**三个关键约束**（详见 `INTEGRATION.md`）：

1. **本包（除 adapter.py）不得依赖宿主内部结构** —— 保证能复用到其他 Agent
2. **不是所有能力都能 MCP 化** —— `Constraint Guard` 必须宿主集成（MCP 协议做不到"拦截别的工具调用"）
3. **符号索引是唯一真源** —— 存在 `backend/necessity/index/store.py`，其他模块按 `(workspace, file, content_hash)` 引用，不得重复存储

**文档归属**（全部在本包的 `docs/` 下）：`INDEX.md` → `backend/necessity/index/`；`CONTEXT_PAGING.md` → `backend/necessity/context/`；`GUARD.md` → `backend/necessity/guard/`；`DIFF_REDUCER.md` → `backend/necessity/reduce/`；`ATTRIBUTION.md` → `backend/necessity/attribution/`。

## 5. 实施顺序

> **完整 gate 判据见 `EVAL.md` §4。** 本节给顺序，那节给每个阶段的 go/no-go 标准。

**原则：每个阶段都必须能独立交付产出，且都有 gate 决定是否继续。**

| 阶段 | 做什么 | 依赖 | 时间 | 独立产出 | Gate |
|---|---|---|---|---|---|
| **I0** | 钩子接口 + 空操作挂载 | 无 | 2 天 | 不改变行为 | — |
| **I1** | 埋点 + **基线测量** | I0 | 3 天 | 基线数字 | **Gate 0** ⭐ |
| **S1** | 基础设施：LSP 符号解析 | I1 | 1 周 | 符号索引 | Gate 1 |
| **S2** | **Context Paging** | S1 | 1.5 周 | **token 下降 %** ✅ | Gate 2 |
| **S3** | 基础设施：调用图 + 影响面 | S1 | 1.5 周 | 影响面查询 | Gate 3 |
| **S4** | **Diff Reducer** | S3（可降级） | 1.5 周 | **冗余率** ✅ | Gate 4 |
| **S5** | **Constraint Guard** | S3（可降级） | 1.5 周 | **约束保持率 ρ** ✅ | Gate 5 |
| **S6** | **Failure Attribution** | 前四者的信号 | 1 周 | **归因准确率** ✅ | Gate 6 |
| **S7** | 打通 + 端到端评测 | 全部 | 1 周 | **端到端数字** | 最终 |

**总计约 9~10 周**（含 I0/I1 与各 gate 的观察期；S4/S5 可并行）。

> **原估 8~9 周未计入 I0/I1 与 gate 审理时间**，此处修正。

**⭐ Gate 0 是唯一能在 3 天内否掉 2 周工作的检查，必须先做。**

## 6. 统一评测设计

> **本章为概览。权威定义（任务集来源、指标公式、统计方法、改进闭环）见 `EVAL.md`。**

### 6.1 为什么需要统一评测

单独跑每个能力只能证明「它自己有效」。**只有端到端对照，才能证明整条链有价值。**

### 6.2 对照组

**两级对照**（完整矩阵见 `EVAL.md` §3）：

| 级别 | 组 |
|---|---|
| **增量对照** | A（裸） / B（+Context） / C（+Guard） / D（+Reducer） / **E（全部）** |
| **朴素对照** | **A′（只在提示词里叮嘱）** / B′（无符号索引） / C′（文本层面检查） |

**E 组是最终要报告的。**

> ⚠️ **A′ 是最关键的对照** —— 它代表现状做法。**如果 E 不比 A′ 好，整个项目就没有价值。**

### 6.3 任务集

**完整方案见 `EVAL.md` §1。** 要点：

- 主体从**开源仓库真实 commit 反向构造**（不用 SWE-bench，避免数据污染）
- 补充两类自造任务：**诱导越界**（Guard 专用）、**高冗余**（Reducer 专用）
- 规模 30 个，分**调优集 20 / 留出集 10**

### 6.4 统一指标

| 指标 | 能力 | 定义 | 可比性 |
|---|---|---|---|
| **任务完成率** | 全部 | pass / 总任务数 | ✅ 硬约束：不得下降 >2% |
| 总 token 消耗 | Context Paging | 单任务累计（取中位数） | ⚠️ 需配对比较 |
| 重复读取率 | Context Paging | `R_waste / R` | ✅ |
| **约束保持率 ρ** ⭐ | Guard | `min(存活轮数, T) / T` | ✅ **已归一化** |
| **冗余率** ⭐ | Reducer | 冗余行 / 总改动行 | ✅ |
| 致败定位准确率 | Reducer | 与人工标注一致率 | ✅ |
| 归因准确率 | Attribution | 与人工标注一致率 | ✅ |

> **修正说明**：早期用「约束存活轮数」作核心指标，但不同任务总轮数 `T` 不同，**15 轮未违反 ≠ 40 轮未违反**，跨任务不可比。
> 现改为归一化的**约束保持率 ρ**。详见 `GUARD.md` §1.2 与 `EVAL.md` §2.2。

### 6.5 成功判据

**整条链成功**，当且仅当：

1. 完成率下降 ≤ 2%（硬约束）
2. 至少两个能力的主指标改善达到**大效应量**（Cliff's delta > 0.47）
3. E 组优于 A′ 组（提示词对照组）

> **关于「显著」的定义**：样本量 n=30，统计功效低，**不足以支撑"显著"的强声明**。
> 因此判据用**效应量**而非 p 值，且结论严格限定在本任务集上。详见 `EVAL.md` §6.3。

**失败判据**（任一成立即需复盘）：

- 完成率下降 > 5%
- 某个能力的指标反而不如对照组
- 某个能力的工具调用次数接近 0（说明没被用起来）
- **E 组与 A′ 组（纯提示词）无差异** —— 说明机制没带来增量

## 7. 全局风险

| 风险 | 严重度 | 说明 | 缓解 |
|---|---|---|---|
| **能力太多做不完** | 🔴 高 | 9~10 周是乐观估计 | 每个 S 独立交付；**Gate 0 能在 3 天内否掉 S2** |
| **完成率下降** | 🔴 高 | 信息减少/约束过严都可能导致 | 每阶段都测完成率；作为硬约束 |
| **做完发现没效果** | 🔴 高 | 8 周投入可能白费 | **Gate 0 先验核心假设**；每个能力都有「不完美也成立的产出」 |
| **Agent 不理解机制** | 🟠 中 | 索引/约束不被告知就白建 | 提示词契约是设计的一部分 |
| **机制被绕过** | 🟠 中 | 约束只接了一个写入路径 | 覆盖所有写入路径（`GUARD.md` §6） |
| **评测任务集造不出来** | 🔴 高 | 所有实验的地基 | 先造 3 个跑通全流程，再批量（`EVAL.md` §1.2） |
| **数据污染**（模型见过任务） | 🟠 中 | 结果失去意义 | 不用 SWE-bench；用较新 commit |
| **过拟合测试集** | 🟠 中 | 最终数字不可信 | 调优集/留出集分离（`EVAL.md` §1.5） |
| **算力不够跑不完实验** | 🟠 中 | 690 次运行 ≈ 4 天串行 | 分层跑；并行；按需裁剪（`EVAL.md` §7） |
| **样本量不足以判定显著** | 🟠 中 | n=30 统计功效低 | 报告效应量而非强称显著（`EVAL.md` §6） |

## 8. 面试叙事

### 8.1 30 秒版

> 现有 Agent 工具都在解决「能不能做完」。我关注的是另一个维度：**做完的改动干不干净**——有没有重复读文件、有没有越界改、有没有多余改动、失败了知不知道为什么。
>
> 我做了四个能力分别解决这四个问题，共用一套基于 LSP 的代码结构图。核心指标是**冗余率**——Agent 生成的改动里有多少是多余的，而且定义是**可证明的**（用测试做 oracle，移除后仍通过才算冗余），不是靠行数估的。

> ⚠️ **不要说"这个指标没人测过"**。过编辑已有研究（TRIM、over-editing 度量工具见 `DIFF_REDUCER.md` §1.3）。
> **正确的差异化说法**：判定更严格（可证明 vs 启发式）+ 工程更可行（结构图做一致性组 + 影响面选测试）。

### 8.2 可能会被问的问题

| 问题 | 回答要点 |
|---|---|
| 为什么不做 Agent 本身？ | Agent 能力赛道已被 Codex/CC 占据；**我做的是质量维度，不是能力维度** |
| 这四个是一个东西还是四个？ | 一个系统，四个能力，共享基础设施；能独立交付 |
| 最难的工程问题？ | ① 耦合改动的一致性组（`DIFF_REDUCER.md` §3）② 测试速度（必须用影响面缩范围）③ 约束必须覆盖所有写入路径 |
| 怎么保证不误伤？ | 每个能力都有「不能降低完成率」的硬约束，且都能降级回原状 |
| 和现有工具的区别？ | 现有工具用代理指标猜（行数、次数）；**这里全部基于代码结构语义** |
| 如果做完发现没效果？ | 每个能力都有「即使不完美也成立」的产出（冗余率、归因分类、约束保持率）；且 Gate 0 能提前止损 |
| **为什么不全做成 MCP？** | **Constraint Guard 做不了** —— MCP 协议无法拦截别的工具调用，必须宿主集成。Reducer 和 Attribution 可以做成 MCP，以后能挂到 CC/Cursor 上 |
| **统计上显著吗？** | n=30 功效低，所以用配对设计 + 非参数检验，**报告效应量而非强称显著**；结论严格限定在本任务集 |

### 8.3 一句话卖点

> **别人在比谁的 Agent 更能干，我在量化谁改得更干净。**

## 9. 术语表

| 术语 | 含义 |
|---|---|
| **充分性** | 任务是否完成 |
| **必要性** | 完成过程中是否有多余动作 |
| **基础设施** | CodeGraph——符号解析 / 调用图 / 影响面 |
| **一致性组** | 必须同进同退的改动集合 |
| **冗余率** | 冗余改动行数 / 总改动行数 |
| **约束保持率 ρ** | `min(存活轮数, 总轮数) / 总轮数`，跨任务可比 |
| **约束存活轮数 s** | 首个约束被违反发生在第几轮（绝对值，辅助展示） |
| **调优集 / 留出集** | 用于指导改进 / 只用于最终验证（防过拟合） |
| **Gate** | 阶段性 go/no-go 判据 |
| **降级路径** | 某能力不可用时退回现状行为，不报错 |
